## 2. 架构：三轴是乘法，不是三份相加

这是「为什么能 >3」的机制，也是本文档唯一的核心主张。

三份 harness **不在同一个维度上**，它们是三个正交轴：

| 轴 | 由谁供给 | 它保证什么 | 单独强会怎样 |
|---|---|---|---|
| **送达率** | 通用 harness（马书 36 章 / 十原则 / CC 官方文档） | 答案能不能完整、稳定地生成出来——重试、截断、预算、路由、降级、留证 | 稳但空 |
| **信息量** | knevo 领域 harness | 答案里有多少可用判断——情景树、五维排序、口径拆解、历史类比、决策者推演 | 深但不敢用 |
| **可信度** | 我们自己的领域 harness | 每个数字能不能被证伪——证据分层 L1/L2/L3、缺数显式声明、引用编号、禁无溯源概率 | 可信但没信息量 |

**答案价值 = 送达率 × 信息量 × 可信度。任一项为 0，整体为 0。**

已有实测证据正好落在这个乘法的两端，不是我编的框架：

- **Q4（PQC 90 天催化）我们大败**：knevo 捞到特朗普行政令等多源催化，我们答「未查到实质催化」。
  可信度满分（没编），**信息量为 0** → 乘积 0。
- **Q6（数据安全双红）我们胜**：knevo 在止于 06-29 的残缺数据上手算给出「双红 2-3 天/分位 45-55%」，
  我们明说「盘面系统无该板块独立行」。信息量它高，**可信度为 0** → 乘积 0。

**同一个乘法的两端。** 这就是 1+1+1>3 的来源：三轴互为对方的**乘数**，
补齐最弱那一轴的收益远大于加强最强那一轴。而知道哪一轴最弱，只能靠测。

### 归层判据（沿用第一原则，不冲突）

- 送达率 = 通用层，**宽容**：拦错了是纯损失。
- 可信度 = 领域层，**严格**：一条都不能为了绿灯放宽。
- 信息量 = **新的第三层**，判据是「有没有把已有数据变成可用判断」——
  它既不是格式合法性，也不是事实正确性。之前没有明确归属，这是本次架构补的那一格。

## 3. 落地顺序（按「先造判据」排，不按「先补短板」排）

### 第一刀：跑 A 组 10 题基线 —— 不需要新代码、不需要用户做任何事

理由：
- A 组是日常主力，**从没跑过**，而所有优化都声称改善了它。
- A 组 case 锚定 2026-07-21/23，DuckDB 有到 07-30 的数据——**7-31 缺数完全不影响验收台**。
- 22 份 knevo 快照里 A 组有 9 份（缺 A8/A9），跑完就能直接 head-to-head。
- 唯一成本是 LLM 配额（~10 次，5 小时滚动上限约 15 次）→ **需要用户批准这次花销**。

```bash
python3 -m intelligence.eval.acceptance run --tier high_freq
python3 -m intelligence.eval.acceptance board
```

### 第二刀：把三轴变成看板上的三列

现在看板只有「运行/真值/体验」三列，真值是单一 pass/fail。
按 §2 的乘法，同一份答案要分别对三轴出分，否则**看不出该补哪一轴**——
这是让 1+1+1 真正相乘的接口，也是唯一需要写新代码的地方。

判分来源分工（别全丢给模型）：
- **可信度**：可机判。已有 `claim_fidelity_eval.py`、`expect_facts` 容差、引用注册表校验。
- **送达率**：可机判。已有 trace 的 degrade_count / 截断留证 / `graph_exposure` /
  本轮新增的 `evidence_coverage`。
- **信息量**：只能 LLM-as-judge，**但必须用已冻结的 22 份 knevo 快照 + 台账里的人工判定
  （「Knevo 胜」「各半」「工作台胜」）当 few-shot 锚点**，不让模型自由发挥。
  这是 abc 偏好对真正的用法——不是训练数据，是**判官的校准锚**。

### 第三刀：按基线补最弱的那一轴，而不是按直觉

C10（追问丢上下文）如果在新后端上复现，它比任何题材深度都优先：
多轮丢上下文会把三轴同时打成 0。

### 用户侧闸门（agent 做不了，需要你）

| 事 | 卡在哪 | 代价 |
|---|---|---|
| codex 参照答案 0/28 | `codex exec` 的 local-access sidecar（:57244）503 / 直连 401，**需要重启或重新登录 ChatGPT app** | 免费，通了可全量 28 道 |
| knevo 缺 6 份快照 | 只能你在已登录的 Chrome 里问，再走 CDP 读回 | ≈115 积分/题 × 6 ≈ 690 积分 |
| A 组基线 | 需要批准烧 ~10 次 LLM 配额 | 5 小时滚动上限约 15 次 |

**不建议**为了凑满 28 份 knevo 快照花 3200 积分：它的权威性在框架层不在报数层，
`reference_plan.not_the_oracle_for` 已经把「不该问它的字段」列清楚了。

## 4. 刻意不做的

- **不新建评测框架。** 已有 `intelligence/eval/`（acceptance / claim_fidelity / fidelity_replay /
  gold_review / runtime_backend_benchmark）+ `scripts/dual_blind_*`。重造只会多一套没人跑的台子。
- **不把 aggregate_gate 从 0.0 直接上调。** 注释里写得对：等基线跑出来再定阈值。
  现在设阈值就是拍脑袋，且会立刻挡住所有 PR。
- **不照抄 knevo 的表达层。** 它的无溯源概率（15-20%、25/50/25）是**可信度轴为 0** 的典型，
  PR #158 的「禁数值概率」契约已经正确地拒绝了它。吸取的是情景树**结构**，不是它的数字。
- **不用跨概念覆盖度之类的「知名度代理」当质量信号**（见 `2026-08-01-frequency-longtail-probe.md` §2.3）。
