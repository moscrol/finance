# 条件计数接缝修复（`1b8707c94`）的验证归档

归档的是 PR #809 里 `1b8707c94` 那一笔的证据：`0729692a4` 删掉失联的「满足升级条件中的N条」
之后，拼回句子的接缝处理有缺陷。本目录让「六种句式先红后绿」「五个机制各有专属测试」这两条
主张可以被独立复算，而不用信 PR 正文的转述。

## 为什么需要它

`0729692a4` 自带两条测试并且通过。缺陷不在它测的那个形状里——它测的是
`——**满足升级条件中的2条，…**` 这种带破折号和加粗的写法，而那正好是唯一被处理对的形状。
把探针铺到六种真实句式上，**六种全坏，包括最普通的中段形式**。这是「金标样本本身就编码了
缺陷」的一个实例：拿产物自己的「好样本」去量产物，量不出来。

## 文件

| 文件 | 是什么 |
|---|---|
| `probe_dangling.py.txt` | 探针源码。直接调 `_repair_dangling_condition_references`，六个用例，靠 `cwd` + `PYTHONPATH` 决定测哪棵树 |
| `probe-before.log.txt` | 在 `99c607671`（修复前）上的输出——六条全部语义残缺 |
| `probe-after.log.txt` | 在 `f53004a57`（修复后）上的输出——六条全部完整 |
| `mutate.py.txt` | 变异脚本。逐个拆掉修复里的一个机制，比对红集与预测 |
| `mutation.log.txt` | 变异结果：5 个机制、红集逐一吻合、无一个「红零条」 |
| `receipt-f53004a5.json` | `f53004a57` 上的全量测试收据：12519 passed / 0 failed，`dirty:false` |

## 怎么复算

探针（两棵树各跑一次，对比输出）：

```
PYTHONPATH=<树> python3 probe_dangling.py
```

变异（还原点必须是已提交的干净树，脚本自检每处替换数恰为 1，不对就中止）：

```
cd <closeout 工作树> && python3 mutate.py
```

## 两条读数纪律

- 探针放在中立目录、靠 `cwd`/`PYTHONPATH` 指向被测树。放进被测快照里跑，测的是快照自己。
- 收据按 revision 取时间戳文件，不看 `latest.json`——多棵树并发时它会被别人覆盖。本轮实测：
  `check_test_receipt.py` 读到的是另一棵树的 `d5d212a1`，据此报「需重跑」，而真正对应的
  `20260921T075402Z-f53004a5.json` 就在同一目录里。

## 不在本目录范围内

K3 独立复核**没有跑成**：`pi auth check` 报 ready，但同一条 20 分钟前成功的最小探针随后持续
超时，900 秒的正式复核输出 0 字节。输入和调用都没变，变的是 provider。这是阻塞，不是「无发现」。
