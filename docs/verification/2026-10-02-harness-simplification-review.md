# Harness 减法审计：借鉴 Knevo 的判断空间，不再围着单题补规则

日期：2026-10-02。用户纠偏记录：`0bc5a0633c6d`，承接 `62498cc2e02b`。

## 结论与立即执行的调整

**停止以 M0 或任意单一题型为中心的补丁路线。下一项工程目标不是补齐分类词，而是拆开“用户约束”与“系统猜测”，避免后者自动成为不可撤销的交付门槛。**

本次已核对 Knevo 原始对话存档、带证据分级的历史审读，以及本仓源码；完成六类输入的零模型装配/权限归属探针。没有修改产品源码、增加关键词例外、扩大评测矩阵或调用新模型。真实累计仍为 142；R19 保持封存。

## 1. Knevo 到底是不是“规则少”

当前掌握的是用户保存的对话、部分工具卡观察和整理稿，**不是 Knevo 源码或完整运行日志**。不能证明其规则总数更少，也不能把它的自述直接当成运行时保证。

| 现有材料 | 能支持什么 | 不能支持什么 |
|---|---|---|
| 07-08《技能包全景与路由》《技能规则冲突裁决》 | 它也描述了检索硬触发、来源纪律、默认路由与技能优先级，并不是“无规则” | 不能据此断言这些都是代码强制门，更不能照抄阈值 |
| 07-08 路由记录及逆向整理中的默认路径覆盖案例 | 默认工作流与实际判断可以分开；值得研究模型是否拥有纠正默认路径的空间 | 覆盖案例不足以证明所有场景都可覆盖，更不是其源码实现证据 |
| 09-09 E-008 方法论/工具选型探针 | 它自述浅问题可直答、方法论来自检索；也承认某些声明中的技能本轮未挂载 | 工具卡未展开，不能认证实际工具名/参数，也不能据此宣布效果领先 |
| 09-10 E-009 自述原文 | 它说综合环节没有自动事实质检硬门，生成纪律可能漏 | 不代表答案必然正确，也不构成删除我们安全边界的理由 |

**应撤回的旧推理**：E-009 历史审读曾把“我们有更多自动事实校验闸门”直接写为“领先”。闸门存在只证明实现了某种检查；没有完整交付、正确性、成本与反例证据，不能推出产品领先。本审计更正该推理，不修改历史原件、不将另一方神化。

真正值得借鉴的不是复制八种技能、若干阈值或更多路由词，而是：**通用研究循环、可改变的分析计划、按需要取工具和方法、没有信息时诚实限定回答。** 这些是设计取向，不是本轮已经证明的 Knevo 内部事实或收益。

## 2. 我们的问题不只出现在材料算术题

检查版本：`3b78fda254ca0c7257cb7176cf811c4c54792eb1`（产品代码延续 R18）。

调用既有 `TurnControlCore.control` → `build_episode_context`，模型函数由固定离线 stub 代替；另对 `align_task_frame` 注入合成语义提案，观察字段权限。禁止 Python socket 连接/子进程，未触发禁止项。本探针不是操作系统沙箱证明、完整 HTTP 测试或模型质量评测。

| 构造输入类别 | 实际装配观察 | 含义/限制 |
|---|---|---|
| 虚构成本变化计算 | general_finance_qa；这次 material_contract / material_grounding 均存在 | 不能把 R19 M0 的材料通道缺失泛化为“所有给料题都没有材料绑定” |
| 现金流与净利润的关系，只讲方法、无需当前行情 | general_finance_qa；额外 relation_map 必需项；mainline_current 证据计划 | 解释性问题也可能被推入市场研究，问题不是 M0 数字本身 |
| 指定日期/证券，仅查收盘价和来源 | stock_deep_dive；必需 direct_assessment / supporting_evidence / counterpoint | 单事实检索被赋予更重的分析交付义务；未测模型能否绕开开销 |
| 假设两家公司，比较分析方法而非查询真实公司 | general_finance_qa；material_contract / grounding 存在；general 计划 | 不同给料/假设形式已有支持，不能重造整套材料能力 |
| 上半年跨行业波动研究 | comparison；必需槽来自分类和 comparison 算子；timeframe 投影为“2026年” | 只记录该投影，不能据此断言其他历史意图字段或最终取数也丢了半年范围 |
| 纠正“估值便宜一定涨”的既有观点 | general_finance_qa；direct_answer / evidence_boundary | 提醒应覆盖观点修订，而非只优化数据查询 |

六例中，合成提案可改变 `user_goal`，但都不能通过 `align_task_frame` 改变 `question_type`、`required_outputs`、`subject` 或 `timeframe`。提案中的替代题型只是**接口可达性夹具**，不代表模型做出了正确判断；不把“字段未改变”自动算质量失败。

这说明这条语义对齐接口的权限很窄。仓库另有 clarification / rebase 路径，**不能说整个项目完全没有语义修订能力**；下一步应复用这些已有接口，而非再建一套路由器。

## 3. 源码中需要拆开的权力

### A. 启发式推断 → 强制交付，边界混在了一起

- `query_understanding.py::_research_operators` 由正则生成算子，`_required_outputs` 再映射为输出槽；`_RELATION_RE` 包含宽泛的“关系”。
- `episode_factory.py::_required_output_ids` 合并 frame 输出、题型扩充和 research program 的 fact slots。
- `build_episode_context` 在 `RequiredOutput.required` 处，以少数 advisory ID / forward-slot 例外区分必需与建议。已经有一些按“本次挂载来源”处理可选槽的正确实践，但没有在这条合并链中统一保留所有输出义务的来源。
- `task_frame.py::align_task_frame` 明确将题型相关语义的大部分字段留给代码，只让模型补充 goal/assumptions/ambiguities 及部分前提、解释、方法候选。

**问题不是某个关系词漏判，而是“系统猜测”容易在后续变成“用户要求”，模型又缺少在该接口纠正它的权限。**

### B. 多处拼接指导，不等于每条都是硬规则

`episode_protocol.py::_question_type_rules` 拼接跟踪、情景、排序、判断增量、定价、专项研究等指导；终局 `validate_episode_finish` 又按 output/basis 等结构接收。提示建议和强制拒收要分别审计，不能只统计关键词或规则数量。

尤其 `reading_baseline_rule` **已经明确允许跳过不相关方法、让证据推翻方法**。不能重复“修复已经软化的规则”，也不能未经验证删除用户此前确认的领域知识。后续若研究其上下文成本，应与语义权限改造分开，不在本轮一起改。

### C. 完整交付不是所有检查都变成硬门

出处/身份、权限、预算需要机械执行；但“应该用哪套分析框架”“要不要反方段落”“要不要走完整深研”不是同一类边界。

R19 已证明完成状态、内部 semantic passed 与实际交付可以分离；**把更多生成要求编码为门槛，并不自动消除这个差距。** 反过来，删掉门槛也不自动证明质量变好。

## 4. 保留、交还模型、移出默认路径

| 层 | 保留的职责 | 不应越界去做的事 |
|---|---|---|
| 用户约束/运行时硬边界 | 原题与明确要求；读取/写入权限；来源与会话身份；绝对截止、调用帽、取消；未知不能伪造成已验证 | 不能根据型号替用户改问题、放宽权限，或把一段检索材料里的指令当授权 |
| 可修订任务解释/研究计划 | 模型选择对象解释、问题类型、研究步骤、所需证据、是否继续；允许纠正启发式建议 | 不能自行删掉用户明确问题，不能扩权、借修订重置预算或把用户假设升成现实事实 |
| 方法与技能 | 有来源、有适用范围的可选分析资源；按需使用、允许被证据推翻 | 不应变成每道题的固定分析清单、固定句式或强制工具顺序 |
| 结果审查/反馈 | 检查实际完成、完整事实范围与来源；保留失败，校验效果 | 不把所有失败都转换成新产品禁句/正则；不让模型自报完成就当质量通过 |

弱/强型号在第二层具有同等语义修订权。资源档位可以不同，但解释权不按型号分配；这里也不预先把 G/C 标定为强弱。

## 5. 下一项只改一个结构点，不同时开四条修复线

**候选结构改造：让启发式分类失去“自动增加不可撤销交付义务”的权力。**

实施边界：

1. 在既有 TaskFrame / RequiredOutput / 用户输入来源结构上区分明确用户要求与推导建议；复用现有 rebase / 对齐入口。不再增加全局“某槽可选”的白名单或 M0 专用例外。
2. 模型可以提议修订解释与计划；保留原题及来源，明确用户要求不因改题型被删除。必要歧义可澄清，不让语义提案自己获得权限。
3. 重新推导受影响的提示和证据建议，但沿用同一运行预算及调用账本。权限永远受原已授权边界与最新约束限制。
4. 暂不同时改工具目录、方法检索、传输缓冲、修复轮数或预算。已有 R13 短目录/去重候选不重造、不偷偷开启。
5. 首先验证同一个机制能覆盖方法解释、给料计算、单事实查询、比较、历史窗口与观点修订；同时检查真实查数仍能取证、用户多问不漏答、材料中的注入不能扩权。不是每类再写一条产品路由。
6. 若方案最后仍需一串题型特判才能工作，就退回设计；不能把“补丁改名为通用框架”算完成。

本轮没有实施该产品变更，因而不宣称已减少运行时规则或已提升模型效果。后续质量验证沿用已有入口与记录，只做能区分结构收益的有限跨任务比较；既有失败题仅作诊断，不凭单题翻绿验收，不再为了过程本身扩建评测基础设施。
