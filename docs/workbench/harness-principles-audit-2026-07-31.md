### `e5d32e80` 值得单独记：锁存要分状态类型

马书原则六「锁存以求稳定，状态抖动比次优状态更有害」的前提是**该状态不应变化**。
beta header、cache TTL 资格属于配置状态，锁存正确；而 `ResearchGap` 是**认知状态，
会被解决**。`add_gap` 只进不出，等于把「本轮还缺 X」锁成永久否决——实测一条早期临时
缺口让 79 轮里 68 轮没跑过 composer。

> 补充规则：锁存前先问这是配置还是认知。认知状态需要解除路径。

## B 类：踩了「行为硬编码」反模式，已部分纠正，仍有提示词侧迁移空间

| commit | 现在的做法 | 反模式在哪 | 该迁什么 |
|---|---|---|---|
| `cf002f25` | 标题「是否夹带未绑定事实」由字符正则 `_FACT_LIKE_HEADING_RE` 改判为「事实词/数字在证据里有无出处」 | 原实现是**用字符正则猜模型意图**（含「跌」即判违规），典型的行为检测器 | 「标题只能用证据里出现过的事实词」本身是**写作约束**，应写进 composer 系统提示词；代码侧只保留 error 级硬拦作为兜底 |
| `7ff05676` | judge 报的序号对不上，按 issue 里引用的原文重新定位 | 我们在**事后猜 judge 指的是哪句**，而 judge 本可以直接说清楚 | 改 judge 提示词让它输出 `quote` 字段（引用原句），定位逻辑随之消失 |
| `3c832917` | 展开聚合 claim 的行绑错，事后重绑到逐项 claim | 根因是**没告诉模型该绑哪个粒度**，然后在下游修 | 「展开聚合 claim 时必须绑到逐项 claim，不要绑回聚合」写进 composer 提示词 |

三条共同形状：**registry/契约里本来就有正确答案，但从没告诉模型，于是在下游写检测器补救。**
和 `13557fab` 前半（required_outputs 进 prompt）是同一个病根的不同表现。

## C 类：安全网，保留但应随提示词侧生效而降低触发

| commit | 内容 | 说明 |
|---|---|---|
| `3e0ee177`（invalidation 部分） | 必需分支被 composer 删掉时确定性补回 | 「必需输出不能缺」是结构性的，安全网有理由存在；但 required_outputs 进 prompt 后触发频率应下降。**若它仍高频触发，说明提示词侧没生效，要查而不是加固** |

> 这两条是**可观测指标**：它们的触发率是「提示词侧是否真的生效」的探针。应该埋点统计，
> 而不是当成永久基础设施。

## 按原则该做而**完全没做**的

| 原则 | 现状 | 差距 |
|---|---|---|
| **马书④ A/B 测试一切** | **零** | 8 个改动全是 big bang。没有对照组，「改好了」只有 canary 观察，没有量化。AI 系统的行为变更影响通常不是「崩溃」而是「不够好」，正是最需要对照组的场景 |
| **马书② 缓存感知设计** | **零** | 每轮 brief/compose/judge 三次调用都在重建 prompt，`registry_block` 每次不同、无静态/动态边界。这是成本和延迟的大头；而刚加进 prompt 的 `required_outputs` 恰好是**稳定内容**，正适合做前缀稳定化 |
| **马书⑤ 先观察再修复** | **做到了** | 离线复现台、逐轮 shadow 统计、真实数据回放——本次做得最好的一条 |
| 可观测性 | **半成品** | `deterministic_issues` 有 code/severity，但没有聚合视图，全靠手写脚本统计 79 个 run 目录 |
| **9.10 制度 > 个人技巧** | **半成品** | 有 CLAUDE.md、skills、handoff；缺统一的「验收定义」——owner gate 与 task_fulfillment 曾对同一轮给出相反结论 |

## 建议的下一步顺序

1. **B 类三条往提示词侧迁**，同时保留代码兜底，并埋点统计 C 类触发率。这是对
   「提示词到底能不能承担约束」的第二次对照实验（第一次是 `13557fab`，结论是有效）。
2. **补 A/B 能力**。哪怕只有「开/关一个 flag + 比较 degrade 率与 gate 通过率」也比全量发布强。
3. **缓存前缀稳定化**。把 `required_outputs`（稳定）与 `registry_block`（每轮变）分到
   缓存边界两侧。
4. **聚合 vs 逐项粒度审计**。`3c832917` 只修了公司表这一处；同一份内容以两种粒度进
   registry 是 composer 反复绑错的根因，需要全量排查。

## 一条不打算改的判断

harness-books 9.1「把模型当不稳定组件，不当队友」作为工程默认值成立，但不等于把模型
排除在判断之外。judge 能指出「'技术性修复更可信' 被升级成 '可能形成有参与价值的反弹'，
新增了未在 evidence 中出现的投资价值判断」——这比我们任何确定性规则都精细。本轮所有
judge 相关的修复（`13557fab` 后半、`7ff05676`）都不是去替代它的判断，而是**保证它的判断
被正确执行**。这个方向要保持。
