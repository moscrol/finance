# 2026-09-22 判官超时归属诊断

## 背景

前次真实验收的末次判官收据只有 `timeout_asked=74.8955`、`TimeoutError` 和随后 0 秒拒发；这个数字是获批额度，不是实际调用墙钟。需要在不调用真实模型、不增加生产预算、不操作 8792 的前提下，区分 HTTP 空闲读取超时、整次请求绝对截止和语义判官共享窗拒发。

## 方法

新增 `scripts/review_probes/diagnose_llm_timeout.py`，只启动 `127.0.0.1` 本地 HTTP 服务，仍走生产 `llm_refine.complete`、`chat_with_tools`、`synthesize_messages_stream` 和 `SemanticEpisodeVerifier._run_judge_once`。新增 `intelligence/tests/test_llm_timeout_diagnostic.py`，钉住本机边界、零预算不发请求、共享窗第三槽零秒拒发、根期限与共享窗归因分离、收据不可覆盖和外部地址拒绝。

## 结果

诊断工具代码提交：`6f084297b7228fced1d214582f8b63992f495a99`。准确收据：`/Users/a77/.finance-runtime/adaptive-timeout-diagnosis-20260922/transport-6f084297b.json`。

- 非流式 `complete()` 获批 0.8 秒时，响应体持续滴流约 2.95 秒仍成功；响应头/响应体停顿才在约 0.803 秒失败。响应头与响应体各延迟 0.56 秒时，总耗时约 1.14 秒仍成功。说明 `urlopen(timeout=...)` 是 socket 空闲等待上限，不是绝对请求截止。
- 工具流式持续滴流约 2.95 秒成功；未形成完整 SSE（服务端事件流）行时约 3.27 秒才交付，也未被总时限打断。
- 合成流式的定时器在完整行滴流和半行场景分别约 1.45/4.38 秒结束，虽然最终拒绝结果，但都超过其 1.2 秒获批时间，现有定时器不能当作严格墙钟证明。
- 判官共享窗两次慢失败合计约 0.803 秒后，第三槽实际请求数为 0，`timeout_asked=0`，根期限仍有余额，归因为 `semantic judge window exhausted by prior attempt`。
- 判官持续滴流约 2.94 秒后返回有效报告，状态为可用；这证明当前判官尝试执行器会接受越过 `timeout_asked` 的完整响应，不代表完整发布链或报告内容通过。

严格探针故意以非零退出，因为当前代码存在上述超时越窗；`--assert-deadline` 是修复验收闸，不是本轮通过标准。提交后定向测试 `14 passed`，pytest 收据为 `/Users/a77/.finance-runtime/test-receipts/20260921T183634Z-6f084297.json`。

## 结论与边界

已定位为：本次覆盖的共享预算分配和零秒拒发有效；在途 HTTP/流读取没有统一的绝对墙钟截止。旧收据的末次请求入口到下一拒发入口间隔可由同一根期限余额相减得到约 75.056 秒（393.498931 - 318.442974），含调用、解析和调度开销，不是纯网络耗时。不能据此把本次滴流缺陷直接认作旧 GLM 超时原因；该判官走非流式 HTTP，旧收据无法区分连接/响应头等待与响应体等待，也无法定位供应商内部原因。
