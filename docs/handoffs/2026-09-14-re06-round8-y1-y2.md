## 根因与修法（一句话版）

两针共用根因：旧合同用同一个 `None` 表达「确认无来源 / 来源未就绪 / 读取失败」，
后两者被折算成「无冲突」放行。修法是把来源身份改成三态（ready / confirmed_none /
unavailable），并用「发布前保存的可信启动身份」把「未就绪」这个状态从运行期消除。

## 关键决定（下轮别再翻案）

1. **取「创建时落身份」而非「显式 pending 状态」**（裁决两条都授权）。理由：消息 API 的
   `create_run` 带上 `maintenance_launch` 后，run 对外可见时身份已就绪——终态折回的裁决
   与消息落盘时序**完全解耦**（窗口前后同一答案，Y1 的窗口不复存在）。pending 方案要在
   消息落盘后再清一次标志，多一次写、多一个「标志没清掉」的失败模式。
2. **接受侧不用记录身份**：Y1 探针 setup 断言窗口期抢登返回 200（R7 合法延伸）。登记是
   乐观路径、不迁状态；收口只在消费侧终态闸。别把记录身份塞进接受侧——会把合法窗口登记
   变成 409，直接违反探针合同。
3. **异常分类**：`FileNotFoundError`（会话不存在）→ confirmed_none——消息入口要求会话
   先存在，不存在的会话永不会有来源落盘，且它是 `OSError` 子类，except 必须先它；
   其余 `OSError` / `ValueError` / `ConversationDataIntegrityError` → unavailable。
4. **补偿登记同走三态**：创建时落的身份与源消息坐标同信任级（都是服务端持久化的客户端
   声明，实质校验在 rejudge 台账回查）。「消息永不落盘」的 run 凭记录身份即可补偿折回——
   裁决要求的「身份就绪后可恢复折回」由此字面落地。
5. **新错误码 `ERR_SOURCE_UNAVAILABLE`（503）**：contracts 追加不改名；unavailable 在
   fold 里被吞成 None（保持 pending），在显式 link_run 里给客户端可重试的 503。
   失败不留半成品、不毒化幂等键（正向测试钉住恢复后重试可折回）。
