# fix/judge-grant-starvation

## 这个分支做什么

修判官窗口的分配缺陷：守卫按 25s 放行、派发却只发 12.5s。

## 当前状态

单笔 `e0b3d543`，已推，**PR #269 open，未合未部署**。干净树。
8792 跑 `a97bfd57`（不含本分支）。**单独部署它不改变任何可观察行为**——
判官照样超时，见下节。

## 未验证 / 已知边界（核心困境，先读这段）

**这条修复不足以让 grok 判官跑通，差得还很远。**

按适配器真实 argv 实测（`--max-turns 1` / `--json-schema` / `effort=low`）：
真实判官 prompt（系统 1259 + 请求 4488 字符）需 **39.5s / 40.7s**。

合法上限：单发 `min(cap 30, window*0.5=25)` = **25s**，共享窗 50s。
**没有任何合法配置装得下 40s**——整窗给一发也有 `cap=30` 顶着。

今天两发判官全灭是**结构性**的，不是抖动。本修复把两发都变成 25s 真机会
（原 25+12.5），但 25 < 40，照样够不着。

⚠️ 未解释：凌晨长电 `run_20260820_032317_442540` 同样 12.5s 窗却
`judge_status=passed`。活 40s、窗 12.5s，凭什么过？**没查**。
不查清它，任何「判官修好了」的结论都不可信。

## 下一步（四条路，需用户拍板，别自己选）

1. **抬窗口**（cap 30→45、窗 50→75）。踩 `R-20260816-07` 绊线，
   `R-20260816-10` 写死「地板 50 / 首轮 25」。延迟实测已有，够不够格用户定。
2. **压 prompt**（4488 字符砍到 25s 内）。**不碰绊线，建议先试。**
3. **换快的独立判官**，保住独立性、放弃 grok。
4. **接受判官常缺**，`judge_status` 拆 `skipped_no_draft` / `provider_error`，
   让收据说实话。

选 1/2 前先把上面那条长电疑点查了。

## 踩过的坑

- **探针必须复刻适配器 argv**。直调 grok 漏了 `--max-turns 1` /
  `--json-schema` / `--no-plan`，它跑飞，报出 >120s 假数，差点据此断言
  「结构上不可能」。带齐后 40s。**不忠实的探针把健康组件测成坏的**。
- **有测试用「数 `synthesis_timeout` 次数」的假 deadline**
  （`RetryWindowClosesAfterTypedFailure`）关重试窗。多算一次窗口就错开它的
  计数器、无关测试变红。窗口只算一次、两条循环复用。
- **判官有两条循环**：`provider` 与 `primary_judge`，改一条另一条照样漏。
  `monkeypatch judge_provider→None` 的测试走后者。
- 别拿「报价之和 ≤ 窗口」当墙钟不变式的代理：静态划分取消后不再等价，
  要用会走钟的假判官直接测。

## 工具沉淀盘点

无新脚本。「探针须复刻生产 argv」在 `10_knowledge/` 已有同形条目
（harness warm-up 那条），本轮是它在 CLI 参数维度的第二例；未脚本化——
判据是语义的，会退化成人肉维护的 flag 清单。
