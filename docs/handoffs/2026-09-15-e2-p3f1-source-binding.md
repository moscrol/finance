# E2 P3f1：真实消息来源绑定，未认证历史输入全链

## 背景

P3f“一律清空历史”已在 `418f2bc9` 反证撤回。它既删合法用户材料，又将已知无材料变成
旧接口的未知上下文。P3f1 不复活清空策略，而先解决一个可局部验证的问题：TaskFrame
中的材料 ID 究竟来自谁。原实现从渲染字符串的 `user:`/`assistant:`/`## ` 重新切消息，
助手正文可以伪装用户，用户正文也可能被角色字样或标题截断。

## 按发现顺序

1. 八个真实 run_turn→默认 decide_turn 探针在基线4F/4P、禁止尝试0。
   四红是助手伪装、用户角色正文、用户标题正文、summary-only；截断材料例本轮已绿。
2. 新增纯服务 `conversation_materials`，从 completed 用户 Message 提取已有 MaterialRef
   和 message_id。不可变投影不保存正文，不将来源资格升级为市场事实或跨轮权限。
3. ConversationContext 保留既有文本行为，同时按同一 summary 尾窗口保留完整消息。
   部分截断的记录不入投影，summary-only 不能假装用户来源；保留完整较早及最近材料。
4. 当前材料合同明确 material_only 才启用。默认 controller→TaskFrame 接线；空投影有
   权威性；运行时 legacy frame 重建共享投影；注入 controller 的旧签名不加必需参数。
   增加消息坐标、快照/去重、scope/签名、空投影、legacy控制，focused33P、回归249P/0禁止。
5. 相邻 orchestrator/integration 两文件110P，但启动器100次禁止尝试、exit3，整体失败。
   83次版本Git探测、16次用户目录扫描、1次 localhost:3456 地址解析。后者14层栈不足以
   归属上层生产者。随后无审计110P/249P/检查器15P，仅保存dirty收据，不作隔离通过。
6. 曾口头误判 Episode 工厂会继续从字符串引入伪装材料；进一步读取发现 material_only
   已将历史串清空，故撤回这一尚未证实断言，也没有修改 Episode 工厂。历史材料正文
   是否送达是后续独立问题，不能因本片身份正确就称交付正确，更不能临时扩成全链重写。
7. 临时worktree分别断开controller投影、移除角色检查、撤完整窗口筛选，结果6F/27P、
   2F/31P、2F/31P，均0禁止尝试。恢复全部候选33P；开发树最终八文件249P/0禁止。
8. 基线应用+最终八针为6F/2P；多出的两红是后来新增的来源坐标断言，不改写初版4F/4P。
   最后临时树六文件再次恢复，hash记录见归档。应用及测试六文件固定字节，原日志不改。

## 方案对比

| 方案 | 评价 | 结果 |
|---|---|---|
| 按数据范围一律清空历史 | 既伤授权材料又混淆已知空/未知 | 已反证，不采用 |
| 增加角色/标题正则补丁 | 正文与消息信封仍混在一起，规则越补越脆弱 | 不采用 |
| 从实际Message角色/坐标形成投影 | 不依赖渲染文本猜可信身份；复用既有材料ID | 本片采用 |
| 取所有存储历史或半篇尾文 | 扩大窗口或把片段铸成新材料，无法代表原输入 | 不采用；同一窗口只取完整记录 |
| 全模式强推新参数 | 非本片需求，破坏旧注入controller签名及旧语义 | 只对明确material_only接默认路径 |
| 只有绑定不对后续局限明示 | 可被误读成模型历史已干净/正文已送达 | 产品门明确列出未覆盖接缝 |
| 放松审计限制获得110P | 绿断言可能吞过越权尝试，不能替代0尝试 | 失败及无审计收据分别保留 |
