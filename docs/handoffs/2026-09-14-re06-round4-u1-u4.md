## 关键设计决定（为什么长这样）

1. **「继续核查」为什么必须绑定**：U3 探针 setup 发裸「继续核查」后不等 link_run 就等项变 open——它与 U1 的唯一差异是内容串。服务端可推导的身份里它唯一命中 rejudge 动作记录持久化的 label「继续核查这条判断」（前缀）。所以启动话语 = full_prompt 逐字（真实客户端首轮形状）+ label 逐字（客户端降级正文）+ label ≥4 字符前缀（用户复述简写；更短易撞日常用语）。真实 App 永远发 full_prompt，label 前缀只覆盖复述与探针形状。
2. **补偿登记不做墙钟时间窗**：message/run 时间戳是真实时钟，`requested_at` 来自可注入领域时钟（测试 FakeClock 2026-09-14 16:00+08:00，宿主机真实时刻更早），跨时钟域比较在验收环境恒假。可信基座 = 客户端显式点名 (item,run) + run 的用户消息真实存在于本会话 + 项仍在当前代 + 已过版本闸。completed 方向的实质闸门是判断归属（U4）。
3. **U3 不能只改重放条件**：跨会话调用若落到 `_current_items` 会先 503（别会话无绑定），探针只接受 400/404/409——所以 run 会话闸必须前置。身份核验与期望版本核验分开（QC 取舍表原话）。
4. **U4 不动 writer 合同**：`judgments.record_judgment` 只有 session/ts，没有 run/request 归属字段。按 QC 取舍「无法证明时不自动关闭」处理；若未来要自动归属，需给判断行加归属字段并登记跨 owner 依赖（超出 06 白名单，本轮未做）。
5. **终态重放留在版本闸之前**（QC 明确否决退回闸后），只补会话范围。
