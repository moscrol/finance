# 双远程镜像边界与本次收尾 · 2026-09-30

## 背景与发现顺序

1. 用户指出全局盘点遗漏 GitHub 云端分支。实查同步前 GitHub 591 条分支、Gitea 590 条，共有的 590 条全部同 SHA；唯一缺项为已经实现测试隔离的云端分支。本轮将其取回并复制到 Gitea，双方均为 `4129bdad96d55c9e1b5da8bc281247cabbff6335`。
2. 检查发现 origin 实际是公开的 `moscrol/finance`。因而从最新 main 新建只含共享文档的分支；本地旧研究分支没有直接推 origin。
3. 但将旧研究分支的完整交接推入 Gitea 后，GitHub 自动出现同名分支。此前“Gitea 私有，所以只推 Gitea 可作为内部归档”的判断错误。
4. Gitea API 确认已有到 GitHub 的 push mirror：提交触发开启、周期 8 小时；该配置早于本次操作。当时先保留配置，准备具体处置并请求确认。
5. 核实误传分支仍是本轮推送的原 SHA 后，验证本地 Git bundle 可恢复，保留本地分支与工作树，依次撤下 Gitea、GitHub 的本轮新建引用。读回两端均无该引用，main、测试候选和共享文档分支未受影响。
6. 最后 fetch 发现云端测试分支的跟踪记录从 3d2b1ba99 被强制退回 4129bdad。回查记录：11:07 已取到 bca700858，11:21 已取到 3d2b1ba99；现有镜像随后以 Gitea 旧头覆盖了新头。本轮文档推送会触发该镜像，因此停止继续推文档，先在本地分支及经验证 bundle 保全两提交，再用普通快进恢复 Gitea 候选，回读 GitHub 也恢复到 3d2b1ba99。
7. 新提交已包含 Mac 原补充测试，本轮确认测试函数语法树一致。候选的完整门禁仍须绑定最新头验收。已提出停用强制镜像的用户确认项；镜像配置在取得回答前未改。
8. 用户回复“执行”后，于 11:56（Asia/Taipei）移除这条镜像配置，API 回读 `/push_mirrors` 为空；原有提交触发和 8 小时任务随该配置停用。未改变仓库可见性、主干和生产服务。随后核对双方 592 条分支全部同 SHA，主干75693271、候选3d2b1ba99均保留。后续交接采用显式逐分支普通快进推送；没有安装新的后台同步任务。
9. 12:02 发布共享交接时，先普通推送 Gitea 到149145c45，读回 GitHub 仍停在4835a66e3、镜像列表为空；再显式普通推送 GitHub，双方才同149145c45。随后全量核对发现 GitHub 分支数量减少，DeleteEvent 指向 `arena-ai-coding-agent[bot]` 的同期删除。本轮保留该清理现场，不重建缺失分支、不向 Gitea 传播删除；主干、候选及交接分支仍一致。

## 决策

| 方案 | 判断 | 结果 |
|---|---|---|
| 只将内部报告推私有 Gitea | 漏查后续公开镜像，私有标签不能代表传播边界 | 撤回该方案，修正交接 |
| 保留原件与 bundle，再撤下本轮新建远程引用 | 可回退自己的误传，保留后续接续依据 | 已执行 |
| 重写整个远程历史或改变仓库可见性 | 影响所有协作者，超出本次分支同步 | 未执行 |
| 另加一个反向强制镜像 | 会扩大双端互相覆盖风险 | 不采用 |
| Gitea 单一集成、云端回收、仅快进同步 | 能把分叉作为待处理状态，而非覆盖掉 | 用户已确认；强制镜像停用，改为按需逐分支同步 |

## 验证与限制

- 处置后的双端快照：各 592 条分支，同名 SHA 全部一致，无单端独有分支。该数值只是核对时刻的快照。
- 这张快照曾掩盖云端提交被回退。后续恢复结果以 3d2b1ba99 为候选头；一致性检查还需要本地已知推进记录，不能只比较两个当前头。
- 停用后的另一次全量比较发现并行分支删除；不能用 earlier 的592条全等结论覆盖这个新差异。缺失引用留给清理线按删除原因及接替记录核对，不盲目双端补齐。
- 两端 main 为 `7569327143a9a40ff44da32d723865b062d856e6`；本轮无主干合并或部署。
- 内部原件、本地分支、经验证的 bundle 和两端 refs 收据留在本机。删除远程引用不保证已公开 Git 对象或缓存已清除；本轮没有证明完全撤回公开内容。
- [Gitea 官方说明](https://docs.gitea.com/1.25/usage/repository/repo-mirror/) 明确 push mirror 会强制推送并覆盖目标变更。这正是本次停用该配置、改用普通快进的原因。
- 本轮的共享文档回读证明交接可达，不证明测试候选已验收；最新候选和基线的完整收据应另行对比，本轮没有签该门禁。

## 接续

使用 [双远程协作流程](../workflows/dual-remote-collaboration.md) 按需回收新云端提交并分列双方 PR。若以后需要持续自动同步，再实现并验收独有分支保全、分叉拒绝、并发与网络失败处理；当前没有新自动任务。

手段沉淀为现有 Git/API 的核对流程及 AGENTS 入口；用户批准的是停用旧镜像、暂用普通快进，因此复用 Git 已有机制，没有扩成新的远程写入程序。可迁移教训是发布前沿镜像链核最终可见性，不能仅凭入口仓的 private 字段判断。
