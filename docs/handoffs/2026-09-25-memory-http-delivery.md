## 按发现顺序

1. fetch 后主干固定为 `1751e21e0fd30642e0b223604b64b30e38c46f41`；旧分支明显落后。merge-tree 预检只发现经验文档文本冲突，运行时代码自动合并，但这不是语义兼容证据。本轮未开始实际 merge。
2. 读取真实 HTTP 路由和装配器，确认可在 provider 回调边界替换模型，保留 API、TurnOrchestrator、判题、用户绑定、注册表和 Episode。用户、数据、检查点与部署台账全部隔离在临时目录。
3. 新测试由 HTTP 创建会话，以 ConversationStore 预置合成的已完成答案，再由 messages 路由发纠偏。写侧核对 provenance 与主体；这不验证上一条答案的生成。
4. 下一研究轮刻意另开空会话。否则纠偏原句可能通过 conversation_context 回显，让“首请求包含原句”的断言绕过记忆链也变绿。
5. 首次试跑发现 pytest 在 fixture setup 后又设置 `PYTEST_CURRENT_TEST`，保护门因此跳过写入；将删除标记放到临时根建立后的 test call。随后改正对模型正文的断言：它使用 E 编号与来源文案，不暴露内部 evidence tier。两次失败均为夹具问题，没有据此改生产逻辑。
6. 同用户命中、另一用户空、撤回后空三例通过。读取真实检查点核对入口身份、记忆类型及 content hash；socket 与模型工具调用守卫均为零。
7. 仅新增测试提交 `3047cb1ee2f9347aeb65142b8c484559d248c372`。干净树重跑原 P0/P1 加 API 与会话集成测试，794P/0F/0S；同 SHA 收据校验通过。

| 方案 | 评价 | 结果 |

| 同会话搜纠偏原句 | 聊天历史也可送达，无法归因记忆台账 | 否决；使用新空会话 |
| 伪造 controller 或 adapter 的成功答案 | 无法证明 HTTP 装配和首请求送达 | 否决；只替换外部模型与市场预取 |

| 缺前置就调用真实模型验“用对” | 超出当前授权与 #76 前置 | 不执行；采用、质量 UNKNOWN |
