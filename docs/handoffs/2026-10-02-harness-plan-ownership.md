## 按发现顺序

1. 旧 PLAN 的 answer_elements / branch_goals / perspectives 保留规则会把模型自己的研究设想变成不可撤的承诺；同时任务合同、hash 与 v1 恢复/授权快照耦合，不能简单改一处 hash 或重建 context。
2. 增加显式 `base_revision` 和 `revision_reason`，以已接纳 PLAN 作串行修订基线。原无基线记录保留旧规则，显式升级可行，升级后省略基线拒绝。撤回自拟项可至空，仍不写原请求、必需输出、期限或根预算。
3. 在真实 Episode 消费回路验证：计划更新进入后续输入和 outcome，旧证据与已报告分支用量保留；计划项清空仍不能让漏必需输出的 completed 终稿通过。JSONL 事件往返保持 hash；不由此声称新增恢复执行器。
4. 前期消费者探针发现 `FulfillmentItem` 丢 required，导致「必需项也缺」时把可选缺口混进补写/失败投影。将已有必需性沿 item、missing_required、报告和失败投影保真；repair 直接消费正确清单，无需再增补写分支或调用。
5. 真实红测发现：无效 PLAN 携工具，第一次得到格式提示，第二次却会落入普通派发。两条 loop 均闭合每个工具回执，一次提示后再失败即走原终局，不增加重试。deadline flush 也不得替未接纳新协议计划执行工具。
6. 解析器放开撤回后，adaptive 指令、checkpoint 与进展仍要求逐字保留会自相矛盾，故同步模型可见基线和约束；静态指纹明确更新并留原因。SDK 自有 loop 没有 PLAN 接纳点，本片未新增。
7. 产品提交 `12555e9adef541ee1350e1567bffa5253df2f61c` 后固定回归1044P/1S、9变异捕获。复核时补强旧式合法 PLAN+工具在 deadline flush 的正例，测试提交 `7513d476b90c82d9a6fbcef453879999c90c915e`；产品不再改，重新在此 pin 跑相关1045P/1S及全部9变异，前后核心321P。
