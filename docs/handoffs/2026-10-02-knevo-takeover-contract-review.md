## 选择与被否方案

| 方案 | 评价 | 结果 |
|---|---|---|
| 再加否定/边界/同义词规则，翻绿已见题 | 跨任务已出现同一代理失真；枚举增长仍不能证明意思正确 | 否 |

| 只加 origin 或扩大可选槽白名单 | 消费者可丢来源，反馈还能把建议升回必需 | 否 |
| 一口气重写总架构、工具目录、预算与收尾 | 无法区分收益来自哪项；已有并行 owner 与候选 | 否 |
| 保留窄身份补丁和红例，单独评审 P1 权力流 | 能定位共性而不掩盖旧缺陷，不触碰其他补丁栈 | 采用 |
| P1 复用现有 PLAN 单入口 | 已有计划 revision、事件和 loop；须同步处理单调限制与真实消费者 | 建议，未实施/未获独立裁决 |
| 现场直接 rebase 并替换 task_frame_hash | 历史事件、终局和恢复快照将不再指同一份合同 | 否 |
| 根请求身份稳定，解释单独版本化 | 保住原题/权限/账本，模型可改工作理解；代价是 snapshot/恢复同改 | 建议，未实施 |

采用的是“控制面减管辖权”，不是少验证。用户明确要求、来源/假设身份、授权和资源仍受保护；不同型号共享语义权。模型对自然语言的解读不因附一个 origin 标签就成为用户确认。
