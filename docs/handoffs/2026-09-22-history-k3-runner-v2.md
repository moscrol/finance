## 为什么重做执行边界
上轮两个启动阻塞已复现：受限shell的here-document需要临时写盘；controller sandbox里再次sandbox-exec被macOS拒绝。宿主认证成功和四个Python替身分支不能证明完整审查链通过。

| 方案 | 决定 | 原因与边界 |
| --- | --- | --- |
| 给旧shell放开TMPDIR或继续嵌套sandbox | 不采用 | 前轮已有失败原件，且不能只修一个启动点就宣称完整隔离修好 |
| 只删外层sandbox、继续开放任意bash | 不采用 | 会把任意命令及秘密读取交给模型，不能称隔离等价 |
| 可信宿主 + 限制协议worker + 单层sandbox | 本轮采用 | 宿主持token和发送；模型只得read/search/git，所有工具从同一worker授权并单层禁网/禁写。宿主本身无OS沙箱，这是明确的信任边界 |
| Pi请求前hook抛异常限额 | 不采用 | 已安装Pi的emitBeforeProviderRequest会捕获异常后继续发送，不能作fail-closed预算闸门 |
| 真正发送前代理预占额度 | 本轮采用 | 同一事件循环检查/预占之间无await；失败也占额。只约束本地发往sidecar的HTTP请求，不证明sidecar内部尝试次数 |
| 提示词要求留时间 vs 强制关闭探索 | 两者配合 | 第18次请求或400秒撤工具并注入收口要求，24次/600秒硬帽。能留收口机会，不能保证模型真的给终稿 |

Pi SDK使用明确模型、空资源加载器、内存会话和关闭retry/compaction的设置，不读取个人扩展、技能或记忆。凭证初始化核原resolver脚本SHA后直接执行同一Python正文，无shell here-doc；stdout仅进宿主内存。真实token不传给工具或Pi进程，Pi仅持随机的本地代理凭证。
