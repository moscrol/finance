## 五条缺陷与修法

### T1（P1）：终态早于第二个 HTTP 请求，合法复核无法登记/收尾

真实 UI 次序：先 `POST messages` 拿 run_id，再 `POST actions(link_run)`；服务端在消息响应前已提交执行器。
模型立即失败时 run 先于登记到终态 → Q3 关联闸（终态无登记一律 400）把合法复核永久卡在 rejudgment_requested。

**选定方案**：消息接受侧建立可信关联。`create_message` 在 `create_run` 之后、`submit_conversation` 之前调
`facade.bind_pending_rejudge_run`：本会话恰有一条当前代复核请求时，把新 run 按与 link_run 同构的形状
（同 stable_id、同 request_event_id）登记进 run_links。观察器终态收尾随即可用这条关联折回。

配套改动（否则探针仍红）：观察器先折回后，迟到的客户端 link_run 会在 apply_event 预检处再撞一次迁移
（项已 open，rejudgment_requested→failed 不再合法）→ 400。因此在 `_maintenance_action` 加终态折回的
**全局幂等**：基键未见但派生键 `link_run:{item}:{run}:terminal` 已录 → 在版本闸**之前**直接重放折回结果。
放版本闸之前是因为折回本身推进了 management_revision，迟到调用的期望版本几乎必然过期——但「这个 run
的折回结果是什么」是唯一确定的答案，重放零迁移，也不要求客户端先刷新。

会话归属问题：`management.rejudgment` 不存 conversation_id（01 合同，不动它）。用「产生了当前
request_event_id 的那条 rejudge 动作记录」回查会话归属——动作记录带 conversation_id。
零候选 → 普通消息；多候选 → 服务端不猜，等客户端显式 link_run（保守回退，不是缺陷）。

被否：
- UI 加延时 / 赌先后——评审明令禁止，且治标不治本。
- 删关联闸退回「同会话就行」——Q3 的硬闸是上一轮的正确成果，退回去等于 reopen 洗刷攻击面。
- 内容匹配复核 prompt——探针发的 content（"继续核查"）根本不是 full_prompt（生成的长文本），
  内容匹配会让探针永远红；且用户可编辑文本，信号太脆。
- 给 01 的 rejudgment 合同加 conversation_id 字段——改动 01 冻结合同换便利性，scope 不匹配。

### T2（P1）：关联缺少复核请求身份，旧 run 的迟到回调误收尾新请求

run_links 原来只有 item/run/session/time，证明的是「曾关联过这个项」不是「属于当前这一轮」。
合法取消 + 重新发起 + 旧 run 迟到失败，就会把新请求折回 open。

修法（上一个 session 已落地，本会话只验证）：登记行带不可变 `request_event_id`；`find_run_link` /
`latest_run_link` 加代际参数，**给了代际就 fail closed**（旧台账无代际的行视为不同代，不做通配豁免——
豁免会造一条门禁看不见的旁路，代价只是旧行不再自动折回，用户重新发起即可）；登记、终态折回、
观察器 `fold_run_terminal`、`_upgrade_registered_link` 四处统一核验当前代。观察器路径代际不符时
干净返回 None（不抛异常让观察器吞成 stderr 假象）。

### T3（P2）：新会话首轮选任务丢 source_refs / scope

首轮没有已完成 run → continuation 无 run_id → App 按消息合同（`ContinuationRequest.run_id`
min_length=1）只能发纯文本 → 消息落盘 continuation=None，结构化来源断在边界。

**选定方案**：服务端水合。`select_task` 的完整 continuation 本就以幂等记录存在动作台账里；
`create_message` 在客户端没给 continuation 时调 `facade.pending_task_continuation`：按
owner（台账天然隔离）/ conversation_id（记录字段）/ full_prompt 逐字匹配（钉住 task）三重边界
从台账取回 continuation 落用户消息。内容不匹配 → None，普通消息不硬塞。

被否：
- App.tsx 改为「有 click_payload 就带上 continuation」——消息合同 run_id 非空会直接 422；
  放开合同让客户端自证 task 归属，等于把核验权交给不可信方。
- 要求 select_task 伪造 origin run——评审明写「不要求伪造 origin run」。

### T4（P2）：无 id 读最新总结实际读字典序最大的内容哈希

`list_immutable` 按文件名排序，内容寻址 ID 没有时间序。修法：`_latest_summary` 按 `generated_at`
取唯一最新（`summarize()` 恒定产出，且在 content_id 的 drop_keys 里，不碰冻结体）。

判定矩阵（返修中修正过一次）：初版要求**所有**行带 generated_at，把两个既有合同打破
（q8 与上轮探针种的总结没有 generated_at）。查实生产 `summarize()` 恒定产 generated_at /
protocol_hash 但**不写 supersedes**（supersedes 只在探针合成行里），故最终规则：
单份直取（兼容遗留）；多份须全带时间戳 + 单 protocol 链 + 最新刻唯一；否则 400 要显式 id。
被否：supersedes 链头方案（生产数据没有 supersedes，多版本会全判成多链 → 永远 400）。

### T5（P2）：锁文件打开异常后进程锁永久泄漏

`try_transaction` 原来 acquire 成功后先 `os.open` 才进 try/finally——open 抛错时进程锁永不释放，
后续有界测量全部 StoreLockTimeout，只能重启进程。修法：acquire 后立刻进外层 try/finally，
fd 与 flock 各带取得标志；没拿到 flock 不解锁（解没拿到的锁会踩别的持有者）。
