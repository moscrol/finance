# 2026-09-11 k3nj 臂诞生记：无判官对照臂的定型与 400 墙定罪

## 背景（不读这段会误判后面每个决定）

00 车道（capability-benchmark-00）的 gpt-5.6 基线臂剩 7 题待 resume，前置是两条断线：被测出口
Cockpit 57244（单 Plus 账号周窗 3%，09-16 00:38 才重置）和判官 grok Build（402 余额耗尽，
账号级，无自愈）。用户提出：「判官换成 glm 不就好了，而且 llm as judge 甚至可以关了，
knevo 都没有」，随后拍板「执行无判官版」。本文是这个决定的完整执行记录。

关键事实核查（决定执行前完成）：

1. **判官不是评分器，是被测系统的一部分。** episode 管线是 结构校验 → 语义校验
   （`SemanticEpisodeVerifier`，3500 行判官模块）边审边修；00 臂终件的「26/31 轮
   passed/repaired」就是判官修出来的。生产 8792 此刻 env 就是 `judge=auto + grok-cli`。
   00 单存在的全部理由是「生产形状读数」，中途换/关判官 = 换被测系统 = 混臂。
2. **「判官全关」在配置层不存在。** verifier 在 `api/app.py` 装配层无条件构造；
   `ASK_EVIDENCE_JUDGE=off` 关的是另一个东西——知识库召回的语义相关性闸（检索闸）。
   可达的「无判官」= unset LLM_JUDGE_* → 判官回落主模型自审，receipt 有
   `correlated_judge=True` 一等字段记录这种形态。
3. Knevo 没有判官是 Knevo 的生产形状；本仓的生产形状有。「无判官」要作为**新臂**
   存在，不能给 00 臂打补丁。

## 坑（可迁移）

1. **bash 3.2 + UTF-8 locale：`$VAR` 紧跟多字节字符会把首字节吞进变量名**，
   set -u 下报「`rev` +乱码: unbound variable」——报错里的变量名是张冠李戴的。
   一律写 `${VAR}`。00 臂 preflight-00.sh 有两处同款未修（NO-GO 分支才炸）。
2. **探针请求形状 ≠ 真实流量形状**（00 车道地雷#1 的同族）：网关探针不带
   temperature/thinking 字段，字段级 400 永远探不出。解法是 preflight 断言配置本身
   （shim 值、judge 撤离），不是靠流量探针。
3. `grep -c pat || echo 0` 在无匹配时输出两个 0（grep 打印 0 且 rc=1）。
4. 两把钥匙两套门禁：同网关同模型，不同凭证路对字段的接受集不同。排障时
   「我探过 200」先问用的哪把钥匙、带的什么字段。
