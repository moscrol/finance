# 测试门禁：独立收据与进程写入权

## 背景

接管302132旧分支的首次全量中，测试进程通过，但包装器损坏的LATEST变量与读写目录协议不一致让门禁失败。继续审原工具又发现共享latest、失败收据读回返回0、零执行和身份不完整的风险，因此在main基准728f3271另树修复，不把设施改动混入回填模块。

## 实施与反例

1. `013289c2`：shell每轮分配唯一 `gate-*/pytest.json`；conftest支持目录/显式路径、随机默认文件名与独占创建；latest原子更新仅作导航。新 `scripts/main_gate_receipt.py` 核计数深结构、非零执行、退出码/failed_ids、解释器、dirty、revision，以及本轮树和真实进程退出码。显式baseline比较只做红集诊断，不批准带红合入。初版旧实现21F/1P含两条helper尚不存在，不能统计为21个语义漏洞；相关修复47P。
2. 完整组合 `321712b6` 反证了“唯一文件就足够”：嵌套真实 `pytest --collect-only` 继承父路径，先写0计数；全量12059P/85S/2X结束后，父进程被不可覆盖规则挡住。读回正确拒绝，门禁4。原零计数JSON和日志保留，没有补写测试结果。
3. `d5d807f805629c7e3458d3de0e6954afb287eb69`：pytest configure阶段先登记owner进程ID；继承父路径的后代不写父收据；新顶层shell清外层owner后重新认领。真实子进程反例覆盖普通环境和继承外层owner，旧版均失败，修后四个相关文件49P。实际故障来源 `intelligence/tests/test_pytest_collection_scope.py` 又经同一门禁1P/1S且读回一致。
4. 新组合 `e1b63b1a5b7c066b7377bbd2d005051863331001` 在另一独占检出重新跑全部叶子，不覆盖第一组合。结果与SHA256清单归协调分支 `ops/worktree-ownership-closeout-0921` 的 `docs/verification/2026-09-21-ownership-recheck/README.md`；失败轮在同分支 `2026-09-21-ownership-followup/`。

## 方案对照

| 采用 | 否决 | 原因 |
|---|---|---|
| shell分配唯一输出，读写共享协议 | 运行结束读latest | 并发另一轮能替换导航，目录契约可能不一致 |
| 独占创建原件，导航原子替换 | 秒级时间戳+短SHA直接覆盖 | 同秒同版运行也可能撞名 |
| configure阶段认领owner | finish时才认领/仅靠唯一文件名 | 子进程可能早于父结束并继承同一输出路径 |
| 同时核进程和收据退出码 | 只核文件可解析 | 读取动作成功不等于测试成功 |
| 保留红收据，再测新组合 | 人工把12059写回旧JSON | 事后修证据破坏真实发生顺序 |

## 结论边界

#814已推，仍WIP。49P是提交前作者验证，组合收据只签明确固定SHA，不移签这份文档尖；源码diff check通过，历史原件空白不清洗。首尾Git采样不证明期间无人改后还原，仍需独占树。PID是合作进程间归属标记，不是抵御同用户恶意写者的安全沙箱。

没有独立Spec/Quality签字、main合入、生产改动或付费外审。本轮准备了固定输入审查包，但未发送自动队列。通用模式已回写harness-reference独立PR14及既有证据卫生笔记；原脏BUILD未改。一次性三叶编排器只归档为本轮证据，正式门禁与回归在仓内长期维护。

后续取得适当授权下的独立复核；若main或代码变化，生成新组合与新收据。不要用第一轮控制台绿、旧400d02dd收据或共享latest替代第二轮事实。
