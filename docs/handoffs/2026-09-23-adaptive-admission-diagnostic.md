## 背景

## 发现顺序

1. 旧取消探针在行迭代体内才设置 cancel，但假服务只发无换行字节；因此走 deadline 不足以证明产品取消实现有问题。新作者正反例证实这种触发差异，旧原件与 reviewer 标签未改。
2. 旧 HTTP 诊断只有最后阶段，无法把进程创建、请求发送和回收时间拆开；若未触及 HTTP 响应体却准时退出，还会被当成目标场景通过。增加观测和覆盖门，不改预算或停止策略。
3. 检索探针直到全部结束才打印；import 在 try 外，120 秒超时后空日志。并且它把 exit 0 直接当 ready，即使子进程打印 ready=false。拆出轻量 worker，flush 阶段与周期栈；父子两侧校验 shape 与终态结果。
4. 每批设置新 PYTHONPYCACHEPREFIX 会绕开已有依赖字节码并重新写缓存。改成允许读现有缓存、禁新写；不因一次新结果就把它认定为旧超时根因。
5. execute 阶段原来先读旧计划/脚本，16 个普通请求额度可能耗于读源码与修探针。输入改为前两工具调用优先执行必红控制及指定作者测试，探索要求查签名与实际触发、失败非零退出。只是提示安排，尚未经新独审证明服从。
