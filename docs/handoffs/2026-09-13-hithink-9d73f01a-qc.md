## 新发现 P1-A：克隆后的 stat 把未进入副本的提交认作基线

落点：`market_feature_store/sync/sync_daily_full.py:483-486`，末端检查在 `:624-632`。

真实顺序：

1. 父进程从 target 克隆出 staging，旧值 `10000` 已进入副本。
2. 在 `clone_to_staging` 完成实际复制、尚未返回给父进程的交接点，让另一 DuckDB 进程把 target 值更新为 `17000` 并干净 close（提交成功、无残留 WAL）。
3. `source_stat = target.stat()` 采到的是**新 target** 的元数据，却把它当成**旧 staging** 的来源基线。
4. 本轮子进程正常提交、交本轮 run_id；校验、库内收据、最终排他锁、备份均走真实实现。
5. 末端 stat 与错误基线相同，父进程仍 `rc=0, swapped=true`。

实测结果（`probes.json → after_clone_before_baseline`）：

| 对象 | 旧日期 total_amount |
|---|---:|
| 刚克隆出的 staging | 10000 |
| 第三方已提交的 target | 17000 |
| 换名前备份 | 17000 |
| 最终正式路径 | **10000** |

这里没有伪造 mtime、没有裸文件攻击；第三方只用受支持的 DuckDB 写连接。备份能手工找回 17000，**不等于这次成功换库没有静默撤销第三方提交**。

修补方向：让“快照内容 + 来源身份/版本基线”来自同一个受保护窗口，而不是事后把 target 的最新 stat 指派给已完成的副本。可在初始克隆阶段持与 DuckDB 写者互斥的共享读锁，允许普通读者、禁止写者，锁内获取/验证来源身份并建立基线；末端仍需当前排他检查。还须防路径替换，不能只依赖 size/mtime 而忽略 inode 身份。最终实现须覆盖 clonefile 及 copy fallback，不要求为整个子进程耗时持生产锁。

## 新发现 P1-B：两轮共用 staging，成功状态能发布另一轮失败产物

落点：`sync_daily_full.py:442,458-466,539,645`；`db.py:249-262`。

固定 `<target>.staging` 是可被任意新父进程清掉的共享名字，`remove_stale_staging` 不验证所有者是否还活着。新 run_id 只校验 status，不保护之后的 staging 内容。

真实双父进程交错（`concurrent-runs.py`）：

1. A 的子进程成功，父进程已消费 A 的正确 run_id、验证 A 的 staging、写入 A 的 `ops_sync_run`。
2. 暂停 A 于拿最终锁前，启动真正的第二个父进程 B（没有替换 B 的清理、探针、克隆和校验逻辑）。
3. B 把 A 的活跃 staging 当作旧残留删除，从 target 重新克隆。B 子进程写入 `failed_child_B` 后 rc=1、不写 status。
4. B 正确返回 `rc=2, swapped=false`，失败 staging 留存。
5. A 恢复。target 没动过，最终锁与备份都正常；A 把当前同名 staging——实际是 B 的失败产物——换进 target，报 `rc=0, swapped=true`。

最终可见表只有 `fact_market_daily, failed_child_B`；A 的 `successful_child_A` 和 `ops_sync_run` 都不在。**B 的拒绝换库被另一个成功父进程绕过，A 的校验与收据也不再描述最终产物。**

这不是排除项里的 `cp/dd` 裸文件攻击：重建 staging 的是仓库自己的正常编排，两个子进程都只通过 DuckDB 写数据。夜跑脚本的 mkdir 锁没有覆盖独立修复 CLI/所有直接父进程调用，不能作为本例的互斥前提。

修补方向（与末端 target inode 锁分工）：

- 优先在公共编排入口增加 **per-target（按目标数据库分开）的运行互斥锁**，在任何 staging/status 清理之前取得，覆盖整个本轮生命周期；所有调用方共用同一路径与身份解析。该锁是独立协调文件，不长时间锁生产 DB、不会阻断普通读者；锁冲突应明确拒跑。
- 或每轮唯一 staging/status 路径 + 只清理已确认无人使用的产物，并为最终发布提供同目标的版本竞争保护。
- 仅给 status 再加 pid/时间戳、或仅在最后多读一次状态，均不能解决共享 staging 在“验完→使用”间被替换。
- 补双父进程回归：至少覆盖 A 已验证/B 失败的交错，以及并发开工不得删除活跃 staging。不得只测两子进程的 DuckDB 写锁。
