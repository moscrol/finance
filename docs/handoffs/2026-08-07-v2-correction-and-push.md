### ② 我制造过一次假警报，用户为此专门下了一条指令

我在上一轮结论里写：「他人 6 个提交全部压在我的 `348428f5` 之上——将来若要单独
处置我的工作，仍会遇到同一个交错问题，**越晚成本越高**。」

用户据此下令「你先把这个解决了」。核验结果是：**这个问题不存在**。

实测两个方向都成立 —— `origin/main` 是 `348428f5` 的祖先，`348428f5` 是 `main`
的祖先。这是**线性栈**，我的工作是 main 的一个**前缀**。前缀可独立快进推送
（`git push origin 348428f5:main` 就是 ff），**不需要重写任何人的历史**，
且与上面压了多少提交**无关**——他人再堆 60 个，前缀推送仍是快进。

我把两件事的成本混为一谈了：

| 想做的事 | 是否需重写他人历史 | 成本随时间涨？ |
|---|---|---|
| 推送我的工作（前缀 ff） | 否 | **否**，与压多少无关 |
| 把我的工作从 main 摘掉、只保留他人的 | 是 | 是 |

第二种只在**否决我的工作**时才用得上，而前缀一旦推送连这个需求都消失。
我把第二种的成本套到了第一种上，让用户为一个不存在的问题下了一条指令。

**给审阅者的可迁移判据**：涉及 git 拓扑的成本断言，先跑
`git merge-base --is-ancestor` 双向确认线性性，再谈成本。
