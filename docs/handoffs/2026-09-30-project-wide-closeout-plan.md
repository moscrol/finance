## 3. 推荐的执行顺序与交付终点

### A. 先收拢可交付代码，停止并行堆候选

1. **回答能力仍是主线。** 从当时最新 `gitea/main` 建干净集成树，列出 #956 的依赖链与实际保留行为。d9 依赖此前材料作者协议，不能只拣一个 SHA 当自足补丁。新 main 没有 v2 时，不要先带入 v2 再 cherry-pick `26c` 撤回；直接得到受审的 v1 状态及退役回归。
2. 候选内容验收固定四类：材料新闻时点、现金流/估值起点、历史追问、真实工具查数。写明真实模型、版本、调用额度、首发结果，逐句检查原题是否答完。把 `completed`、格式合格、确定性判官通过与内容合格分别记录。具体用例与停止条件沿用已冻结材料，先审既有样本，不临时加重试。
3. 允许将“有价值的协议窄修复”与“未解决的财务推理”分开交付，前提是独立验收证明适用行为且未回归其他路径；发布名称只写具体修复。不能再把整个 #956 叫作已追平 ReAct。
4. **方法验证采样拒绝作为独立 P1 修复。** 先读取当前 study 合同、label 版本及拒绝分支，确定是迁移缺失还是输入配置不兼容，再选择最小修复。验收至少包含同版本有效采样、旧协议诚实拒绝/显式迁移、到期回检记录可读；不能改写旧样本扩大历史命中率。
5. 门禁 TMPDIR 修复可先完成以减少后续集成测试的环境干扰；最终与相应代码版本绑定，原 #988 首轮超时和复跑收据原样保留。
