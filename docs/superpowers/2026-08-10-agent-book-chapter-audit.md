## 第 10 章：最重要的一条，它推翻了我们判卷器的立论

书里给了判断多 Agent 是否值得的**核心准则**：

> **协作过程是否引入了生成时不存在的新信息。**
> 如果多个 Agent 只是重新审视同一段文本（如辩论模式），在等量计算资源下单 Agent
> 同样有效；但如果 Reviewer 能获得外部反馈——代码执行结果、视觉渲染截图、
> 工具验证输出——多 Agent 的优势就是实质性的。

**对照我们的 semantic judge** [实测]：

| 判据 | 我们 |
|---|---|
| 用的是什么模型 | **和写答案的同一个 client、同一个模型** |
| 看到什么 | **同一份草稿 + 同一批已绑定证据** |
| 有没有外部反馈 | **没有**——不跑代码、不渲染、不调工具复核 |

**按这条准则，我们的判卷器正好落在"没有引入新信息"的那一类。**

这比第 4 章的批评更深一层：
- 第 4 章说"提议者与审核者应来自不同家族"——那是**相关性**问题，换个模型可缓解；
- 第 10 章说的是**信息**问题——**换模型也解决不了**，只要它读的还是同一份文本。

而它每次要付 15+7.5+7.5 秒的预算（2026-08-09 实测三次全部 `TimeoutError`）。
**在"不引入新信息"的前提下，这笔开销的正当性是存疑的。**

书里还给了正确的方向——事后验证的要诀是**模态切换**（第 4 章）：
不是让第二个模型重读一遍，而是换个模态检验。对我们而言，能引入新信息的验证是：

1. **回查数据源**：judge 拿 claim 去 DuckDB 复算，而不是重读草稿
   （这正是"工具验证输出"）
2. **交叉源核对**：用另一个 provider 的检索结果验证同一条事实

> ⚠️ 但书同时提醒：**多 Agent 的 token 消耗可达普通对话 15 倍，且 token 用量本身
> 能解释约 80% 的性能差异**。所以不是"加一个能验证的 judge"就赢，而是要先算清
> 它引入的新信息值不值这笔钱。

### 预算感知：书里点名的机制，我们完全没有

> 2025 年 Google《Budget-Aware Tool-Use Enables Effective Agent Scaling》：
> **单纯增加 Agent 可用的步骤数并不能保证性能提升**。标准 Agent 缺乏"预算意识"，
> 即使有 300 步预算，仍倾向浅层搜索、很快饱和。要让更多步骤转化为更好结果，
> Agent 需要**显式的预算感知机制**，根据剩余资源动态调整策略。

> 🔁 **本节初稿写"我们从不告诉模型剩余预算"，这是错的，已更正如下。**
> 我当时只搜了 `budget_tool_observation`（那个确实只管字符截断），就下了负面断言。
> 真相是**步数预算一直在传，时间预算没有**——两者差别很大，混成一句会让人去补一个
> 已经存在的东西。发现方式也值得记：是给功能加开关时**跑挂了一条名叫
> `test_next_model_turn_sees_dynamic_tools_and_remaining_budget` 的既有测试**才暴露的。
> 负面断言的代价再次由测试而不是由搜索兜住。

[实测] 修正后的事实：

| 预算维度 | 模型看得见吗 | 在哪 |
|---|---|---|
| **步数**（剩余工具调用次数） | ✅ **一直都传** | `_append_tool_budget_state` 把 `runtime_budget.remaining_tool_calls` 注进最后一条 tool 消息，并附指令 |
| **时间**（剩余秒数/比例） | ❌ **完全没有** | —— |

所以缺口是**时间**这一维，不是整个预算感知。`budget_tool_observation` 名字里有
budget 但管的是工具输出的字符截断，与时间无关——是它把我误导了。

**这解释了 2026-08-09 的一个反常现象**：S3 在题面改对之后工具调用从 3 次涨到 6 次，
然后 `repair_deadline_exhausted`——模型不知道自己快没时间了，仍在广撒网。
书里的处方正是"前期广泛探索，后期聚焦"，而这需要模型**看得见剩余比例**。

## 第 2 章：Agent 状态栏——我们缺的那块显式状态

书的核心主张是：**不要让模型被动地在海量上下文里找线索，而要主动提供经过提炼的
结构化状态**。手段之一是 **Agent 状态栏**——把隐式状态变成显式信息。

我们的状态：

| 项 | 状态 |
|---|---|
| Agent 状态栏 | 🔴 无 |
| 剩余预算可见 | 🔴 无（见上） |
| 已用工具 / 已得证据的结构化摘要 | 🟡 证据在轨迹里，但没有摘要视图 |
| Skills 渐进式披露 | 🟡 有 skills/，但未做成按需加载的目录 |
| KV Cache 友好布局 | ❓ 未审计 |

**状态栏是同时解掉预算感知与批量事件注意力分散的那一个位置**（第 4 章还提到
队列式处理时模型只关注最后一个事件，缓解手段也是状态栏显式编号）。
对我们，最小可用版本是在每轮注入一行：

```
[预算] 已用 42s / 总 90s，剩余 53%；已调工具 4 次；已绑定证据 11 条
```

书的方法论：**观察→假设→实验→验证→新认识→新假设**，把 agent 工程从炼金术

## 第 3 章：记忆与知识库

书的收敛结论是**双层记忆架构**：Advanced JSON Cards 常驻上下文提供"概览"，
上下文感知检索按需提供"细节"。

| 书的要素 | 我们 |
|---|---|
| 用户记忆（结构化卡片） | 🟢 `.foresight/` 台账、experience cards、corrections |
| 知识库 + 检索 | 🟢 DuckDB + 知识图谱 + BM25/向量 |
| 上下文感知检索 | 🟡 有 retrieval planner，是否"上下文感知"未审计 |
| **recall@k 等检索质量度量** | 🔴 **没有**——我们不知道召回够不够 |
| RAPTOR / GraphRAG 式结构化索引 | 🟡 有知识图谱，未做层次摘要 |

🔴 **recall@k 缺失值得单列**：2026-08-09 的 S3 缺 `cause_attribution`，judge 的原话是
"证据只支持盘面观察，证不了归因"。**这到底是检索不足还是题目超纲，我们现在没有
任何指标能回答。** 书第 3 章给的正是这个度量。

## 第 1 章 / 第 8 章：结构对齐，链路有缺口

**第 1 章**：Harness = 约束 + 验证 + 纠正；"生产级 Agent 系统里 Harness 的绝大部分
代码都在做这些保障机制"。🟢 我们确实如此（层级门禁、结构/语义 verifier、
契约不变量、预算控制面）。

**第 8 章**：持续进化要**把在线执行与离线学习分开**——在线记录证据，离线生成并
验证候选更新，再逐步发布、整理或回滚；优先**可归因、可验证、可回滚的局部修改**。

| 环节 | 我们 |
|---|---|
| 在线记录证据 | 🟢 `.foresight/` 台账（corrections/verdicts/interactions） |
| 离线生成候选更新 | 🟡 有夜间回检，但未形成"候选更新"这一层 |
| 验证后再发布 | 🔴 弱——经验多是人工读了再改，缺自动候选→验证→发布链 |
| 可回滚 | 🟡 git 层面可回滚，但没有"这条经验导致了什么"的归因 |

## 追加（2026-08-10）：「分档用错了」这个假设被实测推翻

看到 `deep` 档有 240s / 12 步 / 3 路并行分支，而我们把 S3 因果题声明成
`standard`，我判断预算决策是个伪问题——应该升档而不是抬预算。**实测不成立。**

同一道 case，只改 `tier` [实测]：

| 量 | standard | deep |
|---|---|---|
| policy `total_seconds` | 90s | **240s** ✅ |
| `synthesis_reserve` | 60s | 75s |
| **工具批次上限** | 29.64s | **30.00s** ← 几乎没动 |
| **judge 三次窗口** | (15, 7.5, 7.5) | **(15, 7.5, 7.5)** ← 完全没动 |
| `mandatory` / floor | 不变 | 不变（换档不影响 floor） |

**升档对两个真正在超时的组件几乎无效。** 原因是它们各自有**与 tier 无关的硬上限**：

| 组件 | 硬上限出处 | 值 |
|---|---|---|
| 工具批次 | `episode_tool_batch.py:244` `stage_timeout(30.0)` | 字面 **30.0s** |
| judge 窗口 | `episode_semantic_verifier.py` `MAX_SEMANTIC_JUDGE_WINDOW_SECONDS` | **30.0s**（→ 首次 15s） |

`stage_timeout(limit)` 取的是 `min(limit, remaining − reserve)`。deep 档下
`remaining − reserve` = 105s，远大于 30，**所以 min 被那个字面量 30 卡住**——
tier 给的额外时间根本流不到这两个组件。

### 于是问题被重新定位得更准

工具是**并行**执行的（`episode_tool_batch.py:37` 共享 `ThreadPoolExecutor`），
所以一批工具的耗时是 `max()` 不是 `sum()`。而实测最慢的
`evidence_search` 冷调用 **28.2s**：

```
28.2s / 30.0s = 94% 占用率——没有任何余量
```

**需要重标定的是这两个常量，不是 tier 策略，也不是 `standard` 的 90 秒。**
这比"把 standard 抬到 180s"精确得多，波及面也小得多：前者影响生产每一次普通问答，
后者只影响工具批次与 judge 两处。

⚠️ 但 08-09 已实测过：单独抬 judge 窗口会把草稿饿死（两者共用 synthesis reserve）。
**这两个常量不能各自独立调**，要连同 reserve 一起算一次。deep 档 75s 的 reserve
比 standard 的 60s 多出的那 15s，是这次重算里唯一的新空间。

### 实验臂实测：两个改动合起来确实起作用

按上面推导，把两处一起改成实验臂（**未提交，已还原**）：
`tier=deep` + `episode_tool_batch.py:244` 的 `stage_timeout(30.0)` → `60.0`。

| 收据 | rung | structural | missing_outputs | tools | 耗时 |
|---|---|---|---|---|---|
| exp2-1 | S1 | **completed** | **0** | 1 | 90.3s |
| exp2-1 | S3 | **completed** | **0** | 4 | **129.4s** |
| exp2-2 | S1 | **completed** | **0** | 1 | 50.5s |
| exp2-2 | S3 | failed（`model_unavailable`，中转 503） | 5 | 0 | 31.3s |

对照基线（standard + cap 30，5 次 live）：S3 有 4 次 `partial`、1 次 `completed`，
`missing_outputs` 常年 1–5 项。

**三个有效 rung 全部 `structural=completed` 且 `missing_outputs=0`**，
其中 S3 那次跑了 **129.4s**——与前面推算的「S3 结构性需要约 130s」吻合，
而这个时长在 `standard`（总额 90s）下**物理上不可能达到**。

仍未解决的两项：

- `evidence_search:tool_timeout` **仍出现 1 次**（cap 60 下）。说明 28.2s 是冷调用的
  中位量级，尾部更长，60s 不是一劳永逸。
- **judge 依旧 `unavailable`**——本臂没动它的窗口（仍 15/7.5/7.5），符合预期。

> ⚠️ **2 次运行、其中 1 次被中转 503 作废，样本不足以定率。** 能确证的是
> 「S3 在 `standard` 下拿不到它需要的时长」这条约束是真的，以及放开后
> `missing_outputs` 能归零——不能据此宣称问题已解决。
>
> 另记：本轮中转极不稳定，小请求、大 prompt、带 tools 的请求各探 3–10 次全部 200，
> 但 episode 期间反复 503/URLError。**探活通过不代表跑得完**，
> 这也是为什么收据里的 `model_errors` 必须保留——三次实验里有两次靠它才认出
> 「不是我改坏了，是中转挂了」。

换用户提供的 cockpit 中转（`localhost:57244`，本地网关，模型只有
`gpt-5.6-sol`，无 terra）后重跑。**注意这条中转 2026-08-08 曾因上游凭证归档

（远好于 terra 在 x.ailzd 的 21.8s）；长输出 1/3 成功，**195s / 8242 token**。

### 三个臂的结果

| 臂 | 配置 | 结果 |
|---|---|---|
| A | standard + cap30 + judge30 | S3 常年 partial，judge 0/6 |
| B | **deep** + cap60 + judge30 | 结构 3/4 completed；**judge 仍 0/6，全部 15/7.5/7.5 超时** |

`judge60-1 S1: status=completed / structural=completed / semantic=passed`，
其余两个 rung 是 `semantic=repaired`（规格同样接受）。

### 判据：judge 就是需要 >15s，我此前判错了

实测耗时 **13.3–24.1s 横跨 15s**——这正好解释为什么 15s 窗口下 **0/6**、
25s 窗口下 **6/6**。§5.7 把「窗口过小」判为 refuted 是错的，§5.11 已更正，
这里是最终实证。

**当初那个实验之所以失败，是因为它在 standard 档做**：reserve 只有 60s，
judge 拿走的每一秒都直接从草稿里扣。deep 档 75s 的 reserve 才让两者同时装得下。
**同一个改动，在错的档位下会得出相反结论**——这是本轮方法论上最贵的一课。

臂 C 里 S3 的新失败是 `tool_budget_exhausted`（12 个工具槽用尽，deep 的
`max_steps=12`），而不再是超时。**失败模式从「没时间」变成「查得太多」**——
这是个健康得多的位置，也正是第 10 章预算感知该解决的问题。

## 方法论备注

书里有一条与我们 2026-08-09 的教训完全同构，值得并置：

> **（第 4 章）大多数工具调用失败的根因不是模型不知道工具能做什么，而是不知道
> 工具不能做什么。Agent 频繁选错工具时，优先检查工具描述。**

我们照做了，**而实测推翻了它在我们这里的适用性**——两个工具都是 `tool_timeout`，
不是选错。判据本身没错，是**套用前没验它的前提**（"模型选错了工具"）。
