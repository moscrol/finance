# 02 · 深读检索 · 范围外阻塞项

> 合同要求：需范围外改动的记这里，继续范围内工作。每条写清「在哪、为什么是能力损失、白名单内怎么绕、建议谁改」。

## B-1 模型可见证据 detail 一律截 240 字（`intelligence/services/tool_result_budget.py`，不在白名单）

- **现象 [实测]**：Engine A 每条工具结果进模型上下文前经 `research_harness.project_tool_result → budget_tool_observation`，`MAX_EVIDENCE_DETAIL_CHARS = 240`、`MAX_OBSERVATION_CHARS = 900`，并对模型声明「被截掉的原文没有工具可以取回」。kb_search 每条命中送达 1200–1600 字（命中块 + 相邻块），模型只见前 240 字；web_fetch 取回 6 段×800 字，模型见页首 6×240。这是「找到了却没读到答案」的第一损失点，在任何检索改进之前。
- **白名单内的绕法（本单已做）**：深读结果按 ≤240 字切成段落级证据（`kb_rag.DEEP_READ_ITEM_CHARS` 与该常数钉同值，`test_deep_read_item_chars_pinned_to_model_visible_detail_cap`），web_fetch 定向选段同宽。模型看到的是整段，代价是证据条数变多（每次 kb_search 最多 +15 条）。
- **建议**：由拥有 `tool_result_budget.py` 的负责人评估：① 按工具给 detail 上限（取页 / 深读类 600–800 字），② 或把「没有工具可以取回」这句改成指向 kb_search 再读该节的动作（本单已在观察值里给了「同页其余章节」目录）。不动它本单也能达标，但 240 字仍会把长表格的一行切两半。

## B-2 工具契约文案仍按工具名把 web_fetch 一律说成二手（`intelligence/services/research_tool_registry.py`，04 已开工故不改）

- **现象**：`_TOOL_CONTRACTS["web_fetch"]`（约 :1191）与 `["web_search"]`（约 :1177）写死「属二手公开材料」。本单已在证据标题与观察值里带出发布主体 / 文档类型（`agent_research.classify_web_source`），`evidence_tier` 仍是 `public_web`，分档规则归判官（01）。
- **建议**：04（PR #682）合入后，由接手注册表的人把 web_fetch 契约改成「按观察值里的发布主体 / 文档类型使用：官方披露平台与监管机构页面是官方原文，媒体页面才按二手」；kb_search 契约补一句「返回里带『深读』段落与『同页其余章节』目录，要读某节就用 kb_search 检索『页名 章节名』」。两处都是文案，不改参数面。

## B-4 模型网关 cockpit-cliproxy（localhost:57244）不在运行 → live 验收当日无法完成（环境，非代码）

- **现象 [实测 2026-09-09 15:17]**：自起实例（8802，加载本工作树，健康页已核 `code_root`）跑冻结题 dr-19：澄清门先问一句、回一句后进研究车道，三次 `model_turn` 全部 `LLM 调用失败（URLError）`（provider `openai`，`FORESIGHT_BUILTIN_LLM_BASE_URL=http://localhost:57244/v1` 与生产 8792 环境逐字同），`llm.used=false`，答案是「现有证据不足…可直接重试」模板。`curl http://127.0.0.1:57244/v1/models` 连接拒绝（rc=7），`pgrep -i cockpit` 无进程，`launchctl` 只剩 `com.cockpit.codex-auth-watchdog.plist.bak-idle-pin-20260819-0950`（看门狗 08-19 已停）。生产启动脚本自述「cockpit-cliproxy 不可达；先起 Cockpit Tools 再 kickstart」——需要用户启动 `/Applications/Cockpit Tools.app`。**同一时刻生产 8792 的任何研究 run 也会这样失败**，与本单无关，但值得用户知道。
- **本单做法**：不代用户启动 GUI 应用、不切回 09-06 已弃用的中转配置；离线两段（候选召回 → 进入模型可见）已按生产检索模式测完，live 第三段（最终使用）等网关回来立刻跑（脚本、实例、冻结集、澄清回复都已就位：`~/.finance-runtime/cap02/launch-8802.sh {baseline|treatment}` + `scripts/cap02_deep_read_acceptance.py live …`）。
- **顺带发现（给 01 / 运维）**：生产启动脚本钉的判官二进制 `~/.grok/downloads/grok-1.0.5-macos-aarch64` 已不存在（自动更新清掉，符号链接 `~/.grok/bin/grok` 指向 1.0.24），生产判官调用会失败并被降级成「复核服务不可用」。本单自起实例改用符号链接。
- **顺带发现（给 05 输入理解）**：「今年3月淡季动力煤和主焦煤的价格怎么走的？」被澄清门拆出「月淡季动力煤」当候选主体，问「你问的是月淡季动力煤还是煤炭板块」；问句本身并不含歧义。

## B-3 知识库索引 14 天年龄门（知识库仓 `skills/lib/rag/config.py::MAX_INDEX_AGE_DAYS=14`，跨仓）

- **现象 [实测]**：索引 `built_at=2026-08-31T11:01Z`，按页判新鲜度当前 14362 fresh / 48 stale；但 2026-09-14 起整库过龄，`page_freshness` 会把全部命中判 stale。本单的重读原页恢复（`recover_stale_hits`）能把核对得过的命中救回来（正文取自当前页面、标 `recovered`），但排序仍来自旧索引。
- **建议**：知识库侧在 09-14 前跑一次 `rag update` 或把夜跑接上；金融侧不改这个常数。
