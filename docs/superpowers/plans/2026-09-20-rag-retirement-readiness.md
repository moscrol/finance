# 受管检索进程退役状态修复

设计源为本轮独立 KB 动态验收；实际金融进程在 KB `3a210103` 激活新版后拒绝查询，却仍报告 ready/active。沿金融消费边界修复，不变更 KB 维护者的发布协议。新树从当前 main `4ace5ec2` 开始。

方案比较：把所有查询非零都判退役会误伤参数错误；在 status 中重启会使读取变成发布/恢复动作；仅检查上一次错误会在新版激活到首次查询之间继续误报。选择实例固定受管身份，并在状态与服务边界校验小型 current 元数据。

- [ ] 以实际 `PersistentRagWorker` 复现 normal/full 预热成功 → 激活不同内容新版 → 任何新查询前读取状态仍 ready 的反例。原证据保留于 `kb-design/worker/results.json`，新探针用全新临时根。
- [ ] 实例创建时固定受管 generation、manifest hash、generation root 及实际代码/资料/索引绑定；启动子进程用这一固定环境，宿主环境变化不能给旧实例重新贴新版标签。需要重建时必须使用新实例。
- [ ] 状态读取比较固定身份与小型 current 指针，缺失、损坏、替换、退役皆非 ready；不扫描整个索引、不启动/杀死进程。保留可观察的原因，聚合状态也不能 ready。普通查询参数错误不得一律解释为退役。
- [ ] 查询/预热/恢复边界不能把退役实例重新报告为 ready。不要因 keepalive 或自动恢复重复加载旧根；状态接口保持纯读，当前已有 `ensure_recovery()` 的职责不迁入 status。
- [ ] 无绑定且索引及祖先没有 `.rag-generation.json` 时保持旧的非受管只读路径；受管路径（含软链解析）缺完整绑定必须拒绝，不能回退。不要导入任意运行时知识库代码来完成轻量状态检查。
- [ ] 识别“受管绑定”用生成身份的有限键集及 marker，不能因为普通 `KB_RAG_*` 超时/开关或 legacy 的代码/索引路径配置存在，就误认 legacy 为不完整受管版本。保留这些真实旧配置对照。
- [ ] 失效原因沿 status/服务边界的显式身份检查产生，不从所有非零返回或任意 stderr 猜退役。status 保持纯读；旧进程可以仍存活，但不得被就绪聚合认证成可服务，也不得由自动恢复反复启动旧代。
- [ ] 在现有 `test_rag_worker.py` 及适用 readiness 测试补旧实例在查询前/后非就绪、新实例预热恢复、ambient 环境变化不重标、损坏/缺失指针、合法旧路径、缺绑定受管路径、参数失败对照。若池键相同，旧实例不能被误复用；新实例/旧实例共存时不能掩盖任何实际仍被使用的旧路径。
- [ ] 保留真实双索引 scratch 复验和子进程关闭证据，验证显式回滚后新实例可服务。只使用 hash/BM25，两页资料，无生产索引/网络/真实模型。
