## 二、合同 1：`stock_name` 来源

### 现状是两个口径在打架

| 场景 | 现在怎么做 | 理由 |
|---|---|---|
| 一次性修复器（2026-09-11） | dump 不提供 → **从旧行保留**；新增票取库内历史名并与 spec 交叉断言 | 那次每只票都有人工处置依据 |
| 只读预演（2026-09-15） | **NULL + 报缺口** | 「从昨日或旧源偷偷补值，会隐去缺口与来源」 |

两者在各自场景都成立，但日更只能有一个口径。

### 可选口径

| | 怎么做 | 代价 | 失败形态 |
|---|---|---|---|
| **A** 保留旧行名称 | 新行沿用库内上一条同代码的 name | 零新增采集 | ST 加帽/摘帽、更名、借壳**当天静默用旧名**；且行内 `source` 标签写着 hithink 而名称来自 eastmoney，混源在数据里看不出来 |
| **B** 另接东财快照只为名称 | 保留 f14 采集，每日校名 | 多一条外呼依赖 | 东财挂了当天没名；两源代码口径需对齐 |
| **C** 置 NULL + 声明缺口 | 按 09-15 预演 | 13 处读取点会看到空名，含 agent 主查询 | 不会出错，但会退化 |
| **D** 建独立名册 `dim_stock`（带生效期） | 名称本就是**维度**不是事实，不该逐日重复存在事实表里 | 新表 = schema 变更 = 另需授权 | 名册自身也要来源，问题下移但集中可控 |

### 建议（待裁）：目标态 D，过渡期 B

名称是**慢变量但确实会变**。A 的失败形态是「静默用旧名」——最坏的一类，因为它看起来是对的；
C 诚实，但会打掉 agent 回答里的名称（事实 8）；D 才是根治，代价是动 schema。
B 是唯一既不动 schema、又不静默出错的过渡。

**不建议 A 作为日更口径**：它正是 09-15 预演明确否掉的形状。它在一次性修复器里能用，
是因为那次每只票都有人工处置依据——日更没有这个前提。

## 三、合同 2：`turnover`（换手率）来源

### 可选口径

| | 怎么做 | 代价 | 失败形态 |
|---|---|---|---|
| **A** 置 NULL + 能力声明 | 与 mootdx 路径既有行为一致 | 换手率相关问答退化为「查不到」 | 不会出错 |
| **B** 保留旧行 | 沿用上一条 | 零成本 | 换手率是**快变量**，昨天的换手率对今天毫无意义——比名称严重得多 |
| **C** 从 `circ_mv` 推导 | `volume × close / circ_mv` | 只覆盖子集、且 `circ_mv` 来自 fupanhui | 混源；子集外无值；`circ_mv` 自身时效未验 |
| **D** 另接东财 f8 | 保留东财快照 | 多一条外呼 | 与价格源不同源，两源口径差异需声明 |

### 建议（待裁）：A

理由最硬的一条是**存量已经是 NULL**（事实 7）——选 A 不是新增缺口，是承认现状；
而且这个系统已经有成熟的处置范式：`open_times` 恒 NULL，下游自报「判不了」而非猜（事实 9）。

**B 最危险**：换手率是快变量，沿用昨值是典型的「看起来对」的错值。
若确实需要这一列，**D 比 C 干净**：C 的子集覆盖会让「有值 / 无值」取决于该股当天是不是板块成员，
这种不规则空洞是最难排查的一类。

## 四、合同 3：停复牌分母政策

### 事实：同一个「停牌」，仓里至少四处处置不同

| 位置 | 现在怎么处置 |
|---|---|
| `sector_universe.py:253,1350` | 单只无报价 → 丢掉不进事实表，**进缺口账** |
| `sync/sync_local_sector_members.py:18,24` | 东财无当日值的成员 → **剔除**不留 NULL；以 fupanhui 名单为锚，**复牌当天自动回归** |
| `sync/repair_hithink_stock_day.py:29` | 停牌形态（`close=pre_close`、`amount` NULL）→ **保留旧行** + 声明 |
| `cli.py:729` | 全市场涨停 / 跌停统计**不计** ST / 新股 / 停牌 |

四处各有各的理由，但**没有一条写明「板块涨幅的分母该不该含停牌股」**。

### 要裁的其实是两个问题，现在被混为一谈

- **Q3a 名册分母**：板块有多少只成员——停牌股算不算成员？
- **Q3b 统计分母**：算板块涨幅 / 涨跌家数时，除以多少？

| | Q3a | Q3b | 后果 |
|---|---|---|---|
| **A** 名单锚定 + 缺口入账 | 含（按已发布名单声明数） | 只对有报价的算，同时报「N 只无报价」 | 与 `sector_universe` + `sync_local_sector_members` 两处既有实现一致 |
| **B** 观察分母 | 只含当日有报价的 | 同 Q3a | 停牌多的日子分母自动缩小，板块涨幅被幸存者抬高，且**无迹可查** |
| **C** 保留旧行补齐 | 含 | 用昨收当今收（涨幅 0） | 把停牌算成「平盘」会稀释板块涨幅；与既有原则直接冲突 |

### 建议（待裁）：A

这不是新立规矩，是把**已经在两处跑着的口径**写成合同。

B 的失败形态是幸存者偏差且不可见——分母悄悄变小，数字照样漂亮。
C 与代码里已写明的原则直接冲突：`hithink_stock_preview.py:123`「没有独立停牌 / 交易状态：
不能凭零成交合成一根『正常的平盘 K 线』」。

## 五、签了之后解锁什么

- canonical 日更投影可以定稿；`production_ready` 才可能为 true。
- 板块真实涨幅才有可辩护的算法（现在连分母都没定）。
- 名单 generation 与复权 / 收益窗口的验证才有意义——否则验的是一个口径未定的东西。
