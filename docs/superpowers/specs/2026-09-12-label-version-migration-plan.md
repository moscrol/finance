# 标签口径升版的迁移方案（v3 / v4 / v5 三版并存的收口）

> 日期：2026-09-12
> 触发：复核 #738 时指出「共享库重建前要先补迁移方案」；核实后确认这是 **#671 升 v4 时就欠下的债**，不是 #49 引入的。
> 状态：**方案，未执行**。执行要用户逐步点头（写共享库 / 动在途实验）。

## 1. 现状（只读实测，2026-09-12）

| 处 | 标签口径 | 证据 |
|---|---|---|
| 前向协议 `475597e2…`（双红方法，唯一在跑的方法验证实验） | **v3** | `protocol.json` 的 `label_version` |
| 共享旁路库 `db/history_labels.duckdb` | **v4** | `history_build_meta`（#737 记录的 v4 重建） |
| 代码 `labels.LABEL_VERSION` | **v5**（本单） | `labels.py` |

`method_validation.study._meta` 要求库的 `label_version` 与协议**逐字相等**，否则
`ValueError: labels metadata label version mismatch or absent`。只读复验已确认它现在就会拒。

**后果**：该协议的 `capture`（每日前向观察）与 `recheck`（到期回检）在 v4 库上已经跑不动，
而它的前向窗从 2026-09-10 起算——也就是说 **09-10 之后的在途回检目前是断的**，与 #49 无关。
`status` 仍能出摘要，因为它读的是已落盘收据，不查库；所以这条断裂不会自己冒出来。

## 2. 不可接受的做法

- **不把旧观察改标成新版本**。协议冻结的是「在哪个口径下观察」，改标等于事后篡改实验条件。
- **不原地覆盖共享库**后就算完事：旧库一旦被覆盖，v3 / v4 下的收据再也无法复算，
  `pit` 与「当时可知」全部失去可验证性。
- **不为了让旧协议跑起来而放宽 `_meta` 的版本检查**。那道门是对的，问题在迁移没做。

## 3. 方案：旧协议就地收尾，新协议另起，两个库并存

### 3.1 保留旧库（不动任何现有文件）

```
db/history_labels.duckdb            → 备份为 history_labels.v4-<日期>.duckdb（只读留档）
db/history_labels.v3-<日期>.duckdb  → 若 #737 的 v3 备份还在就一并留档（实测 .bak-v3-20260911 存在）
```

旧收据目录 `methodology/receipts/` 与用户态 `method_validation/` 一律不动。

### 3.2 旧协议（v3）：在旧库上完成在途回检，然后显式封存

1. 用 **v3 备份库** 跑该协议剩余的 `recheck`（`--labels-db` 指向备份），把到期对象结算完；
   `capture` 不再新增——前向观察停在封存日。
2. 在协议目录写一条 `superseded` 记录：封存日、原因（口径升到 v5）、继任协议 id。
   旧 `history` / `capture` / `recheck` 收据**原样保留**。
3. `status` 的立场摘要照旧可读——它读收据，不读库。

### 3.3 新协议（v5）：重建库之后另起，前向从重建日次日开始

1. `build-labels` → `outcomes` 重建共享库到 v5（**这一步才是需要点头的写操作**）。
2. 用同一份方法定义 `register` 一个新协议，`label_version` = v5，
   `forward_start` = 重建日的**下一个交易日**（不是重建日当天——当天的前向观察会混进
   重建前后两种口径）。
3. 历史对照段（`history`）在 v5 库上重跑，得到与旧协议可并排但**不可合并**的读数。

### 3.4 规则收据（methodology_backtest）

重建后所有 v4 收据按 #42 认证门自动降为历史观察（#49 补的 `current_label_version` 检查让
这一条**真正生效**，此前只有「收据彼此版本不同」才切轮次）。四条种子规则需按阶段重跑：
`run/scan --stage discovery → validation → holdout`。旧收据留档不删。

## 4. 执行顺序（每步都可停）

```
① 备份现有 v4 库（只读留档）                      ← 无风险
② 旧协议在 v3 备份库上跑完剩余 recheck            ← 写用户态收据
③ 旧协议写 superseded 记录、停 capture            ← 写用户态收据
④ 重建共享库到 v5                                 ← 写共享库，最需要点头
⑤ 新协议 register（forward_start = 重建日次日）   ← 写用户态收据
⑥ 四条种子规则按阶段重跑                          ← 写收据目录
```

①②③ 不依赖 #49 是否合入；④⑤⑥ 依赖。

## 5. 顺带要补的门（本方案未实现，另立单）

`method_validation` 的版本不匹配现在只在**执行**时抛 `ValueError`，`status` 看不出来。
应当在 `status` 的摘要里显式打印「协议口径 vs 当前库口径」，不一致时标明「在途回检已停」。
否则下一次升版仍会悄悄断掉在途实验——这次就是这么断的（#671 升 v4 至今无人发现）。
