## 1. 目标、非目标与证据边界

### 1.1 目标

1. **语义自主**：模型能够纠正默认任务解释、调整研究路线、选择方法与工具，而不是只能修改“目标描述”。
2. **解释权平等**：不同型号拥有相同的语义修订接口。可以有资源档位差异，不能有“某型号只能走固定路线”的权限差异。
3. **轻任务不被过度编排**：给料推理、方法解释、单事实查询不应仅因命中一个词，就被迫完成整套市场或公司研究。
4. **复杂任务不被表达模板封顶**：在授权资源内，允许多轮取证、反证、改计划和必要的子研究；不以固定段落数、固定工具数或单一分析框架限制答案。
5. **交付优先**：已经取得的有效证据应能形成有边界的结果，不能仅因一个系统附加槽未填满而整篇变成占位答复。
6. **做减法且可验证**：迁移后应退出被替代的语义硬门和重复装配路径，不在旧栈外永久叠加第二套控制器。

“不封顶”不是无限预算。绝对截止、调用上限、上下文限制和安全权限仍然有效；目标是不增加与用户任务无关的人为语义限制。

### 1.2 非目标

- 不复制 Knevo 的技能清单、路由阈值或内部架构猜测。
- 不为 M0、D1、D2 或某个已知失败句添加生产例外。
- 不一次性重写所有 agent、工具、知识库和传输层。
- 不取消来源真实性、访问权限、身份、取消或预算检查。
- 不将所有质量判断编码成确定性规则，也不默认增加独立 LLM 判官。
- 不更换模型、上调预算或改变推理配置来混淆结构改造效果。
- 不将 n=1、单测绿、内部 completed 或 semantic passed 当作质量收益。

### 1.3 为什么提出这个设计

已核源码中，启发式分类可以沿下列链条升级为必须满足的交付义务：

```text
关键词/分类器 → 算子与题型 → required_outputs / 证据计划
             → 提示追加 → 终局绑定与完成判定
```

六类零模型装配观察显示，问题不只出现在给料算术：纯方法问题也可能携带市场研究计划，单价格查询也可能装配成公司深研。`align_task_frame` 当前允许补充 goal 等字段，但不接受对题型、必需输出、主体和时间窗口的修订。仓内另有 rebase / clarification 路径，应复用而不是忽略。

R19 表明预算交接可以真实发生，但取到证据仍可能没有合格交付。它**没有证明**材料分类、提示长度或缓冲方式中的哪一项造成超时；本设计不能预先声称会修好那些超时。

Knevo 资料来自对话与部分工具观察，不是源码。可借鉴的设计方向是可调整的计划、按需使用能力、来源纪律和有边界的回答；不能宣布“规则更少所以一定更强”。

## 2. 总体架构：一个执行 owner，四类状态

```text
用户消息 / 已确认澄清 / 材料与历史
                 │
                 ▼
      [请求与授权快照：来源可追溯]
                 │
       启发式只生成初始建议
                 ▼
      [可修订的任务解释与研究计划] ◄─────────┐
                 │                         │
                 ▼                         │
      [单一 Episode 执行 owner]            │
          │           │                    │
          │           ├─ 直接回答 / 澄清   │
          │           ├─ 取工具定义/方法   │
          │           ├─ 执行工具/子研究   │
          │           └─ 提交语义修订 ─────┘
          ▼
      [来源保留的观察与证据]
          │
          ▼
      [交付：完整 / 部分 / 无有效答案]
          │
          ▼
      [离线质量复核与经验候选；不自动变规则]

横切且不可绕过：权限、秘密保护、身份、绝对截止、调用账本、取消。
```

这四类状态是逻辑职责划分，**不是要求新建四个服务或四套数据库**。优先扩展现有 TaskFrame、ResearchTaskContract、Episode、ConversationStore 和证据记录。

### 2.1 决策权矩阵

| 决策 | 主要 owner | 模型可否改变 | 限制 |
|---|---|---|---|
| 用户原话、材料来源、消息归属 | 输入/存储层 | 否 | 原件不可覆盖；后续用户修改另存版本 |
| 用户明确交付要求 | 用户 | 可重述、拆解、请求澄清，不可静默删除 | 必须保留与原请求的对应关系 |
| 工具授权、数据读取范围、写入许可 | 授权层 | 可申请，不可自行扩大 | 引用材料、工具返回、方法文档不能提供授权 |
| 绝对截止、调用帽、取消 | 运行时 | 可申请资源，不可自行授予或刷新 | 修订、加载工具、重试、分支都计入同一根账本 |
| 题型、主体解释、时间窗口解释、研究步骤 | 模型主导的任务解释 | 可以修订 | 不覆盖明确用户约束；歧义影响取数时先澄清 |
| 使用哪种分析方法、是否继续研究 | 模型 | 可以 | 受任务、证据与剩余资源限制 |
| 某份观察是否来自某来源/时间 | 证据层 | 不可改原件 | 可以质疑其适用性，不能改来源身份 |
| 是否有实质答复、是否全文有据 | 交付记录 + 独立于自报状态的复核 | 可以自报，不可自我认证 | 结构通过与语义通过分列 |

### 2.2 启发式的定位

启发式可以：
- 提供初始题型、可能相关工具、主体候选、时间解析候选。
- 帮助较少规划的模型获得一个可用起点。
- 发现歧义并建议澄清。

启发式不能：
- 仅凭命中某个词，增加不可撤销的用户义务。
- 把推测主体、日期或分析路线写成用户已经确认的事实。
- 因型号不同锁死语义修订能力。
- 授予工具、扩大数据范围或自动增加预算。

## 3. 核心契约：不再把“系统猜测”冒充“用户要求”

以下为逻辑字段建议，不要求照名新增一套对象体系；最终映射应复用现有数据结构。

### 3.1 RequestSnapshot：不可覆盖的请求与来源

保留：

```text
request_id / revision
user_message_refs              原始用户消息及可信角色来源
raw_request                    用户完整问题，不能只保留抽取后的标签
material_refs                  材料身份、所属消息、内容哈希和位置
user_obligation_refs           明确要求在用户请求中的位置
confirmed_constraints          已确认的范围/格式/截止日等
permission_snapshot_ref        由现有授权层持有，不由模型填写
```

**自然语言边界不能靠一个 `origin=user_explicit` 标签自证。**
- 带引文只能证明“用户说过这段话”，不能证明系统解释正确。
- 模型可以提出义务的解释，但不能把自己追加的要求标成用户授权。
- 明确编号、表单选择、用户确认可保留稳定子请求身份；非结构化问句至少保留完整原请求作为必须回答的对象。
- 不为了抽取“用户义务”再建立越来越大的题型词表。
- 对会影响权限或核心任务范围的歧义，维持已确认边界，必要时向用户澄清；不让模型自行采用更宽权限。

### 3.2 Interpretation：可修订解释，不是新的授权

```text
interpretation_revision
request_revision
goal
subject_candidates / selected_subject
question_kind_hint
time_window_interpretation
answer_plan
evidence_needs
method_candidates
assumptions / unresolved_ambiguities
links_to_user_obligations
```

`question_kind_hint` 是组织上下文的提示，不再直接决定一套不可撤销的输出模板。模型可以提出另一种解释，也可以不使用任何专门题型。

### 3.3 Requirement：义务需要记录来源，不能只靠槽名白名单

现有 RequiredOutput 至少应能区分：

| 来源 | 例子 | 处理 |
|---|---|---|
| 用户明确请求 | 指定日期的价格与来源；逐项回答明确编号问题 | 不能静默丢弃；有缺口必须如实标明 |
| 运行时完整性要求 | 来源引用必须存在，消息身份有效 | 硬检查，不受题型修订影响 |
| 启发式建议 | 看到“关系”建议画关系图；识别股票后建议反方分析 | 模型可接受、调整或不采用；缺失不能单独否决整篇 |
| 模型研究计划 | 自己决定先比较两个窗口、补查一项数据 | 可修订；保留简短变更原因，不变成永久义务 |
| 方法/技能建议 | 某分析方法的推荐步骤 | 可选资源，不自动升级为用户要求 |

不能再用不断扩大的 `_ADVISORY_OUTPUT_IDS`、题型豁免表或坏例关键词作为主要区分方式。迁移应复用现有“按本次挂载来源判断可选性”的实践。

### 3.4 ExecutionContext：权限与资源保持刚性

包含原有预算、授权和取消对象的引用，以及本次解释版本。**不是修订时复制一个新预算对象。**

- 每次副作用前读取当前有效权限、取消状态和剩余资源。
- 模型修订不能增加 capability 集、延后根截止或重置已消耗调用。
- 模型可以减少自己打算使用的工具；这与永久撤销用户授权不同。
- 若需要新的授权或用户修改限制，必须经过现有授权/澄清通道。

## 4. 语义修订协议

### 4.1 不增加每题必走的“先规划一轮”

轻任务可以直接答，事实查询可以直接取工具。语义修订是可用能力，不是必须调用的仪式。

逻辑接口可嵌入现有 PLAN / 对齐 / rebase 协议；不得另起一个必须先调用的规划模型服务。

```json
{
  "base_interpretation_revision": 3,
  "changes": {
    "question_kind_hint": "method_explanation",
    "answer_plan": ["解释区别", "说明适用边界"]
  },
  "request_refs": ["user-message:current"],
  "reason": "用户要求分析方法，而不是查询某家公司现状"
}
```

这是示意，不指定必须使用该枚举或固定措辞。提案不能携带可生效的 `allowed_capabilities`、`deadline`、`max_calls` 或“将用户要求删除”的字段。

### 4.2 应用顺序

1. 核对提案基于当前 request / interpretation 版本；旧提案返回 stale，不覆盖新状态。
2. 验证请求引用和字段结构；授权变更走独立通道。
3. 保留用户原题、明确要求与既有权限；对重要歧义返回 clarification_required。
4. 以同一 owner 更新解释版本，重算提示、证据建议及完成覆盖映射。
5. 沿用原预算/取消对象；记录一次轻量语义修订事件。
6. 下一次工具执行按新版本与最新权限检查。

若同一模型返回里同时含修订与工具调用，必须先完成修订裁决，再验证这些调用，不能一边应用新解释一边按旧范围并发派发。首个实现可以暂不支持混合提交，并返回明确、可恢复的协议反馈。

### 4.3 拒绝与回退

- 非法/过期提案不改变已接受解释，也不启动对应工具。
- 模型可在原预算内修正，不另开无限修复循环。
- 不因拒绝提案恢复一个更宽权限的旧解释。
- 达到截止后仅交付已有安全结果或明确失败；不能以“修订中”为由续时。

### 4.4 已有证据的处理

- 原始工具观察不因改计划被删除或改写，保留 request、解释版本、工具身份、参数、时间与范围。
- 语义修订会使旧的“适用于当前结论”判定失效，需要重新确定适用性。
- 有合法证据 ID 不等于足以支持新的主体、日期、集合范围或因果断言。
- 迟到结果照常记账、保留身份；是否能用于当前回答另行检查，不自动接纳过期结果。

## 5. 工具与方法：按需展开，而不是偷偷隐藏能力

### 5.1 工具目录

复用现有工具注册表、实际菜单记录及 R13 相关工作，不复制第二份 capability 清单。

默认上下文可以提供紧凑目录：工具名、用途、输入概览、当前可用状态、读取边界。完整 schema 从同一注册来源按需展开。

约束：
- 授权工具必须可发现；不能按题型或型号只给一个不可逃出的工具子集。
- 目录筛选只是展示建议，模型仍能查询完整授权目录或其他工具定义。
- 加载 schema 不授予新权限，也不改变工具参数契约。
- 实际调用前校验当前授权、schema 版本与参数；目录陈旧时返回可恢复错误。
- 不将“加载定义”伪装为已调用，不将“已授权”伪装为服务一定可用。
- 定义加载消耗的 wall time、上下文和额外模型往返必须入成本比较；提示更短未必更快。

### 5.2 方法与技能

方法是具有来源、适用范围和失效条件的研究资源，不是默认答案模板。

- 保留一小组通用安全和来源纪律；领域步骤按相关性提供或由模型主动读取。
- 模型可以不用某个方法，也可以根据证据放弃它。
- 方法、历史观点、用户偏好不能成为市场事实或权限来源。
- 技能可以封装程序性工具步骤；其内部副作用仍走现有授权、预算和身份记录。
- 不以“用户可能有用”为由将所有指导拼进每个首请求。

`reading_baseline` 已有“可跳过/证据优先”声明。迁移前不得宣称它完全是硬门，也不得直接删除用户已确认的知识。此阶段单独研究投递与重复装配，不夹带语义权限改造。

## 6. 研究与执行循环

### 6.1 一个 owner 管理当前任务

复用现有 Episode。逻辑过程为：

```text
读取当前请求、解释、证据、权限与资源
  → 模型选择：答复 / 澄清 / 取定义或方法 / 调工具 / 修订计划
  → 运行时验证并执行
  → 观察回到同一上下文
  → 继续或交付
```

不是每题强制经过 planning → research → judge → repair 的完整链条；也不禁止复杂任务多轮研究。状态展示必须符合真实执行，不把合理的回到研究阶段记成完成。

### 6.2 资源原则

- 复用根账本、绝对截止和当前预算授权，不为规划、修订、检索、合成各自造无限小预算池。
- 区分全任务根预算、研究子预算和既有专项恢复额度。统一归账不等于把不同层的时限混成一个“90秒”，也不自动增加或撤销已授权额度；迁移前须核对真实父子授权关系。
- 预留调用、原生尝试、HTTP 响应、完整身份、usage 分列；所有物理请求包含重试、子研究与恢复尝试。
- 保留合法的收尾余量；R18 的现有约束不因本 spec 被删除或扩张。
- 模型可请求更深入研究，运行时依据已授权资源决定；不能由模型自己发额度。
- 不用题型专用的“再多给一轮”处理失败。
- 资源档位可以有差异，但同样的语义提案在不同型号上适用同一权限与完整性规则。

### 6.3 子研究与并行

不新建多 agent 框架。仅复用已有子研究通道，并满足：
- 子任务能独立定义目标，确有并行或分解价值。
- 子任务权限不超过父任务，继承根截止/调用约束与取消。
- 父子身份、证据来源和消耗可追溯；子任务不能成为藏模型调用的通道。
- 分支结果是证据或研究建议，不是主任务已完成证明。

当前真实父子链与并发预留仍有未证范围。对应测试与身份条件不足时，本阶段不能默认开启该能力，也不能以增加子 agent 数量作为优化成果。

## 7. 收尾、证据与失败呈现

### 7.1 保留什么，不再强制什么

保留：
- 引用真实存在、来源身份与归属正确、数据日期/范围可追溯。
- 材料陈述、用户假设、真实观察、计算结果和分析推断的身份不混淆。
- 用户明确要求的覆盖情况可检查；缺口如实呈现。

不新增默认要求：
- 每句必须拆成固定子断言、逐句套同一格式。
- 每种题型必须有固定标题、反方段落或某几个术语。
- 每个质量问题都必须启动额外判官或整篇重写。
- 用固定句子/数字组合识别某道已见题并放行。

结构检查只能证明结构；来源存在只能证明可追溯，不能证明整段语义完全正确。需要全文审查的部分仍明确标为未验证，不制造“万能硬门”。

### 7.2 分离运行完成与任务完成

对外/台账至少能区分以下逻辑状态，优先映射现有字段，不立即重造数据库枚举：

| 维度 | 示例值 | 含义 |
|---|---|---|
| 执行状态 | running / completed / failed / cancelled | 进程或本次运行是否结束 |
| 交付状态 | complete / partial / no_answer | 是否覆盖用户任务，是否有实质内容 |
| 来源/协议状态 | verified / incomplete / rejected | 身份、引用与结构记录是否齐全 |
| 语义复核 | not_reviewed / supported / concerns | 全文是否有据；不能由模型自报直接填 supported |

保存状态 completed 不能遮蔽占位答复。内部 semantic passed 不能代替全文验收。

### 7.3 有边界的部分答案

- 如果已取得有效证据且只完成部分用户要求，应交付可用部分并明确未完成部分。
- 一个系统附加建议未完成，不应单独将所有结果换成“证据不足”。
- 不能为了避免空答，确定性拼接未经模型表达或未经来源核对的推断。
- 若现有正文包含无法安全分离的越界内容，不能擅自按关键词删句后冒称合格；在剩余预算内做局部修订，或明确未形成可交付答案。
- “可重试”是用户选项，不是 harness 自动追加真实调用的授权。

### 7.4 不设置无穷收尾循环

所有格式恢复、引用补正与补写使用同一已有资源约束。不能同时在协议层、业务层与外层 driver 各自重复重试。

遇到完整性/隐私/授权问题按既有安全规则停止；普通资料不足可以形成 partial。哪些错误中止整批、哪些只结束单格，在实验启动前注册，不能看输出后修改。

## 8. 反馈机制：经验不自动升格成规则

1. 失败保留原输入、实际轨迹和最终答复，先判断属于数据、语义解释、执行、表达还是评测问题。
2. 单题错误进入经验/回归样本，不自动追加默认 prompt 禁句或路由正则。
3. 方法论作为带来源和适用边界的候选，不能从一个例子推成普遍规律。
4. 用户纠偏通过已有记录通道保存；不把系统自己的猜测记成用户偏好。
5. 跨任务证据支持一个共同机制后，优先修改该机制并退出旧补丁，而不是扩大例外表。
6. 记忆自动晋升、画像更新和生产写入继续遵守既有授权；本 spec 不增加写入权限。

## 9. 与现有代码的落点

| 现有位置 | 目标变化 | 必须保留 |
|---|---|---|
| `query_understanding.py` | 分类/算子产物明确标为推导建议；不直接取得新增用户义务的权力 | 用户原题、来源位置与已有实体/日期候选能力 |
| `task_frame.py`、`turn_control_core.py` | 复用对齐/rebase；扩展可修订解释与版本处理 | 原始请求、已确认约束、澄清历史 |
| `episode_factory.py` | 输出义务按来源组合；解释投影与授权、预算分离 | 既有注册表权限上界、材料限制、根预算引用 |
| `research_tool_registry.py` 与既有目录能力 | 单一来源的可发现目录及按需 schema | 实際工具契约、调用前授权、可用状态 |
| `reading_baseline.py`、方法检索/技能投递 | 后续阶段按需、去重、保留知识来源 | 已有软指导属性与用户确认知识；不直接删库 |
| `agent_episode.py`、事件通道 | 同一 owner 应用修订、执行、观察、收尾 | 绝对截止、调用帽、取消、父子身份与预算交接 |
| `episode_protocol.py`、结果投影 | 用户覆盖与结构安全分开；建议不成为一票否决 | 引用身份/作用域、材料与事实区别、失败留证 |
| 既有学习/纠偏台账 | 保留经验与候选，不自动转生产规则 | 用户确认、来源审查与历史失败 |

提交前必须复查精确目标分支的实际实现。上述是已核基线的落点，不是授权跨树修改或覆盖他人工作。

## 10. 分阶段实施与退出旧路径

每阶段一个可独立裁决的主要变量，单独提交、单独记录结果。整体架构不等于一次重写。

### P0 · 减法审计——本轮已有基础，不扩成长期工程

产物：规则/建议/用户要求的归属，现有接口与典型跨任务失配证据。

结束条件：足以选择第一个结构改造点；不要求先盘完所有模块。六类装配观察只作诊断，不当质量验收。

### P1 · 语义建议不再自动变成不可撤销的交付义务

范围：TaskFrame、义务来源、既有语义修订路径及直接消费这些字段的装配/完成判定。

必须端到端做到：
- 推导建议可被模型修订或拒绝，消费者真的采用新的解释。
- 用户要求不丢、权限不增、预算不刷新。
- 旧版本提案、证据适用性和取消得到一致处理。
- 首次可以直接答/取证，不强制新增规划调用。

仅增加 origin 字段或日志而行为不变，不算 P1 完成。**不同时改工具目录、方法投递、模型配置、缓冲方式或修复预算。**

### P2 · 工具和方法按需展开

前提：P1 的职责边界稳定。

范围：复用注册表和已有目录候选；减少重复定义与无关指导的首轮投递，保留完整授权能力的可发现性。

验收：不仅看输入大小，还看额外往返、任务完成、取证覆盖和模型是否仍能选择非默认工具。未经验证不打开既有实验开关。

### P3 · 统一执行与收尾的责任

范围：复用 Episode，把修订、工具、恢复和收尾纳入同一 owner 的真实状态与资源记录；消除重复重试和系统附加槽导致的整篇占位。

不借此增加预算。子研究能力只有在父子身份、资源继承与取消得到验证后才进入启用候选。

### P4 · 跨任务验收与删除被替代路径

- 检查 P1–P3 的组合效果，不用各阶段局部绿灯推导整体通过。
- 在已验范围内移除旧的“启发式 → 必需槽”强制映射、重复提示装配和特判豁免。
- 保留有用知识与反例记录，不把“代码行少”当成质量指标。
- 兼容层只承担迁移；不得让新旧两套机制永久同时裁决同一任务。

### 回退原则

- 回退到已知版本或单一功能路径，不通过新增题型白名单回退。
- 在途 episode 固定其契约版本；不将执行到一半的任务热切换到另一套解释或预算。
- 失败工件与身份缺口保留，不能用回退后的成功覆盖旧结果。
- 合并/部署仍需用户明确授权，本 spec 不移签。

## 11. 验收：验证机制，不再追着一道题跑

### 11.1 零模型契约/性质检查

复用现有测试系统，不新建评分平台。至少覆盖：

| 性质 | 正向与反向要求 |
|---|---|
| 解释可修订 | 合法提案影响真实装配和后续行为；日志变化而执行不变必须被发现 |
| 用户义务不丢 | 简化分析路线后，明确子问/日期/单位/范围仍在；模型不能自删用户要求 |
| 权限隔离 | 改题型、加载技能、引用材料均不能获得额外权限；用户确认收紧后立即生效 |
| 资源不增发 | 修订、重试、分支不得重置截止/调用计数；取消和迟到结果保持原约束 |
| 来源不混淆 | 题设、历史观点与真实数据能并存且不相互冒充；过期/异窗证据不能自动承接新结论 |
| 无关建议不阻断 | 未采用系统建议不导致已满足用户请求的答案被一票否决 |
| 目录可发现 | 未被初始推荐的授权工具仍可发现并调用；未授权工具仍不可用 |
| 任务复杂度不锁死 | 同一机制支持直答与多步研究，不以固定工具数或模板作完成条件 |

变体应改变表达方式、数据和场景。**不要求同义问题一定得到相同题型枚举；要求用户义务、权限与证据口径保持正确。**

### 11.2 有界真实比较

实施完成后另行预注册，复用现有完整入口、模型身份、物理计数和冻结数据机制。

- 每阶段先选能区分该结构变化的最小配对集合；首批原则上不超过12格，实际数量与预算在启动前明确。
- 跨方法/给料、事实查询、比较或历史研究等不同任务形状选题，覆盖简单控制与真实取证；不是每类都扩建一套固定回归题库。
- 已见 D1/D2/M0 只作诊断，不作为未见收益证明；六类装配例也不是未暴露质量留出题。
- 仅使用已有授权型号，冻结模型配置、资料、入口、顺序、每格与全批预算。改变资源配置应单列，不能冒充结构收益。
- 全部失败、未启动、身份缺口和 usage 缺失保留；不补跑凑成功。
- 控制失败不得跳过。是否提前停止后格在运行前写清；不能在结果出来后追加预算或改变停止规则。

12格是首批规模控制，不是新的正式验收项目，也不解除旧240格禁令。若不足以支持结论，就报告不足，不为获得绿灯自动扩大样本。

### 11.3 成功与失败口径

**主目标**：用户要求完成且全文有据，不是更少规则、更少 token 或更多工具调用。

方向性通过至少需要：
- 简单控制能交付；不能一边控制失败，一边宣布通用改造成功。
- 在不止一种非诊断任务形状上观察到完成/保真恢复，或在同等质量下出现可核对的资源改善。
- 已通过的配对未出现已观察到的退步；发生退步时记录原因，不排除坏样本。
- 结构变更在实际轨迹中生效；没有触发该机制的好结果不能归因于该改造。
- 没有权限、身份、预算或来源完整性退步。

样本不足、n=1、非盲复核只能得出方向性结果，不能证明总体非退步或模型强弱排序。

次指标：实质交付率、占位比例、协议修复次数、实际模型调用、端到端耗时、完整 usage、上下文负担。缺 usage 不作0；缓冲设置下的耗时不等于生产首字延迟或计费节省。

## 12. 最小可观测性与风险

### 12.1 只补足当前架构需要的观测

沿用现有记录，至少能关联：
- 原请求版本、解释版本、义务来源与被采纳/拒绝的修订。
- 本轮实际可见工具、按需加载的定义/方法身份。
- 工具调用对应的解释版本、来源与资源账本。
- 最终用户要求覆盖、交付状态、协议身份及语义复核状态。

记录简短理由和结构化选择，不要求保存隐藏思维链，不把用户全文/凭据重复写入新日志。原有事件足够则复用，不为本设计新建通用监控平台。

### 12.2 主要风险与处理

| 风险 | 处理 |
|---|---|
| “模型自主”变成删要求、扩权限 | 原请求/授权独立持有，修订只能改解释；覆盖与权限分别检查 |
| 要求来源标签只是换名的黑箱 | 保留消息/位置来源与解释版本；模型自报 origin 不能自证用户授权 |
| 放松模板后增加胡说 | 来源/身份边界保留，全文质量另测；不把少规则视为自动收益 |
| 每次修订多一轮模型，反而更慢 | 修订可选、复用既有回合；成本计入比较 |
| 短目录省 token 但增加查找回合 | 保留全目录可发现性，测总成本与完成率，不只测字符数 |
| 部分答案被当完整交付 | 执行、交付、身份、语义状态分开 |
| 迁移时新旧规则同时执行 | 每个阶段明确单一 owner 与退出旧路径；在途版本固定 |
| 又回到“这个题特殊处理” | 若需要不断增加题型例外才能通过，停止该实现，回到责任边界设计 |

## 13. 实施前必须明确、但本次不伪造的事项

以下不会阻止阅读和评审整体设计，但在对应代码切片启动前须写入该切片计划：

1. 既有 PLAN / alignment / rebase 中，哪一个承担提案入口；不同时引入多个竞争入口。
2. 当前各输出槽的真实来源及消费点，哪些迁移后成为建议、哪些确为用户要求；只盘所改切片，不要求全仓大普查。
3. 权限与材料限制的歧义处理如何复用现有控制层；不能让语义模型自行放宽。
4. P1 跨层版本更新、在途工具结果和旧证据适用性如何在现有存储中落地。
5. 每阶段真实比较的题目选择、控制、模型/预算和停止条件；本 spec 不是运行清单。
6. 生产迁移范围与回退版本；在获得授权之前保持研究分支，不部署。

## 最终交付判断

本改造只有在**同一通用机制**让不同任务更容易正确交付、没有把语义权限按型号分配、没有放松安全/来源/预算边界，并且退出了被替代的硬编码路径时，才算完成。

如果结果只是多了一个提案 JSON、一层审核、一批题型规则和更多测试数字，却仍靠单题补丁维持，应判为没有实现本 spec 的目标。
