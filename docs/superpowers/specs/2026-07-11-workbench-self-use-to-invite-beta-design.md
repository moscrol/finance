# Workbench-first 垂直金融 Agent：从自用成熟到邀请内测设计

- 日期：2026-07-11
- 状态：已批准，待用户 Review 书面 spec
- 产品基线：PR #190 `feat/chat-first-skill-workbench`
- 当前阶段：Self-use Maturity（本人自用成熟）
- 后续阶段：Hosted Beta Readiness → 10–30 人 Invite Beta

## 1. 决策摘要

本项目不再把“做一个大而全的大众金融 Agent”作为当前目标，也不重新设计已经完成的 Workbench 界面。

产品路线采用 **Workbench-first 垂直 MVP**：先把现有 A 股投研能力收束成一个持续对话、证据可复核、数据时点透明、可以每天使用的研究产品；先由产品所有者本人连续使用并达到主观成熟认可，再补齐托管 Web 的认证、租户隔离、配额、合规和公开证据发布，最后邀请 10–30 名有一定经验的 A 股个人投资者内测。

两道产品门必须严格分开：

1. **Self-use Maturity Gate**：核心研究工作流是否真正好用、可信、稳定，是否值得本人每天打开。
2. **Hosted Beta Readiness Gate**：外部用户使用所需的身份、安全、隔离、成本和内容授权是否就绪。

多租户基础设施不能替代产品质量；本人尚不愿持续使用时，不进入邀请内测建设冲刺。

## 2. 产品定位

一句话定义：

> 面向有一定经验的 A 股个人投资者的盘后研究 Agent，融合全量市场复盘、题材生命周期、公司基本面、公告新闻、历史研究和可审核证据，回答“今天发生了什么、为什么、影响谁、下一步验证什么”。

### 2.1 核心用户

第一目标用户是：

- 熟悉 A 股基本术语；
- 会看盘、题材和公司逻辑；
- 缺少完整研究团队和稳定信息整理流程；
- 需要减少信息噪音、补充证据、形成可验证判断；
- 不把产品当作自动荐股或跟单工具。

当前唯一必须满足的用户是产品所有者本人。本人认可后，目标扩展到 10–30 名同类邀请用户。

### 2.2 时间定位

首版是盘后研究型产品：

- 交易日收盘后更新全量盘面；
- 公告和新闻按小时刷新；
- 晚间整合新事件；
- 次日盘前展示新增变量与验证清单；
- 不做秒级行情和实时交易信号。

### 2.3 长期目标

长期目标不是堆积更多 Skill，而是形成垂直金融 Agent：

- 理解 A 股市场阶段与题材生命周期；
- 理解公司、产品、客户、收入和产业链传导；
- 具备广度检索与财务颗粒度；
- 能持续承接用户研究历史与纠偏；
- 能对自己的判断做 checkpoint、回检和校准；
- 所有重要结论可追溯、可证伪、可降级。

## 3. 产品成功标准

### 3.1 Self-use Maturity Gate

进入外部内测准备前，必须同时满足：

1. 本人连续使用至少 10 个交易日，并明确表示产品已达到可日常使用水平。
2. 今日市场、题材研究、个股研究、消息解读、自选跟踪五类任务均在真实数据上跑通。
3. 每个交易日的盘面数据、公告新闻和证据状态清楚显示截止时间。
4. 核心工作流成功率不低于 95%；失败时显示原因和降级，不静默输出旧结论。
5. 日常使用不依赖开发者频繁修改文件、手工拼命令或手工修复单次 Run。
6. 固定 Knevo 对照题中，搜索广度、基本面颗粒度和叙事可用性达到可比水平。
7. 保持自身优势：证据可复核、缺数诚实、盘面生命周期、不编数值概率、纠偏与回检闭环。
8. 本人主观认可产品显著节省研究时间，并愿意主动继续使用。

本人认可是一票否决 Gate；机械指标通过但本人不愿持续使用，不进入内测。

### 3.2 Hosted Beta Readiness Gate

本人认可后，邀请外部用户前必须满足：

- 真实账号认证和邀请码；
- 跨用户数据隔离；
- 服务端密钥、配额和成本控制；
- 持久化用户态与任务恢复；
- 只开放审核后的证据和研究结论；
- 隐私、内容授权和合规边界清晰；
- staging 公网环境稳定运行；
- 安全和越权测试通过。

### 3.3 Invite Beta 成功标准

- 10–30 名用户可独立注册、登录和完成研究；
- 激活用户不少于 20 人；
- 第二周留存不低于 40%；
- 核心任务成功率不低于 95%；
- 跨用户数据泄漏为 0；
- 严重事实错误为 0；
- 至少 5 名用户明确愿意长期使用；
- 每次有效研究成本处于可接受范围；
- 日常运行不依赖开发者持续人工救场。

## 5. 产品界面与用户路径

### 5.1 界面原则

保留现有三栏研究界面：

- 左侧：对话列表、搜索、新建研究；
- 中间：持续对话、Skill 调用、结构化研究结果；
- 右侧：证据、时点、检索、记忆、反证、降级和运行详情。

不新增平行工作台，不恢复以大量独立 HTML 为主的产品形态。

### 5.2 今日情报状态

在没有打开具体对话时，中间区域显示今日情报：

- 今日市场一句话；
- 市场阶段、成交额、涨跌家数、涨跌停；
- 容量前三行业；
- 主线与重要题材变化；
- 自选股异动；
- 自选相关公告和新闻；
- 昨日研究假设的验证结果；
- 数据健康与截止时间；
- 动态推荐追问。

点击卡片后，在当前界面新建或继续对话，并携带股票、题材、日期和证据上下文。

### 5.3 五条核心路径

1. **每日使用**：打开今日情报 → 找到变化 → Agent 解读 → 查看证据与反证 → 保存或追问。
2. **题材研究**：输入题材 → 产业链、催化、盘面生命周期、公司分层 → 验证条件。
3. **个股研究**：输入股票 → 公司本体、财务、产业链、盘面、证据、风险和替代表达。
4. **消息判断**：粘贴文本/URL 或点击公告 → 新事实/旧叙事/情绪/待补证 → 影响链条。
5. **自选跟踪**：查看异动、公告、题材联动和旧判断变化 → 一键开启研究。

## 6. 五个正式产品 Skill

用户只看到五个稳定产品 Skill。内部 D0–D9、W7、Theme Radar、RAG、公告工具和历史剧本继续作为底层能力，不直接暴露复杂度。

### 6.1 今日市场

输入：日期或“今天市场怎么样”。

输出：

- 一句话状态；
- 关键指标；
- 主线与风险；
- 自选影响；
- 次日验证点；
- 昨日 checkpoint 回检。

实现基线：合并 Daily Review 与 Daily Agent 的用户输出。事实、系统判断和未来假设必须分开。

### 6.2 题材研究

输出顺序：

> 题材定义 → 新增变量 → 产业链传导 → 盘面生命周期 → 公司分层 → 反证与验证。

必须识别当日、中期和历史类比时间尺度，复用 D4、D6、D8、Theme Radar、情景树和公开证据。

### 6.3 个股研究

输出顺序：

> 公司本体 → 财务变化 → 产业链位置 → 市场为何选择/抛弃 → 证据硬度 → 风险 → 验证条件。

复用实体锚定、D1/D2/D3/D5/D7/D9、公告互动易和 stock-deep-dive 契约。补齐单季还原、现金流、资产负债异常、业务分部、可比公司和证据有效期。

### 6.4 消息解读

输出顺序：

> 发生了什么 → 新在哪里 → 影响链条 → 受益/受损分层 → 市场是否已交易 → 需要补什么证据。

支持文本、URL 和产品内公告；与过去 30/90 天事件比较，区分硬事实、观点、传闻和情绪。

### 6.5 自选跟踪

输出顺序：

> 今日变化 → 对应旧逻辑 → 新证据/反证 → 是否值得研究 → 一键追问。

Self-use 阶段沿用本地用户态；内测阶段迁移为服务端用户自选。不记录真实持仓成本和仓位，不生成自动买卖信号。

### 6.6 统一 Skill 契约

每个产品 Skill 必须声明：

- 输入 Schema；
- 权限；
- 超时和成本级别；
- 数据依赖；
- `modules/citations/warnings/as_of/raw_result_ref`；
- 无数据、超时、模型失败时的降级；
- quick、standard、deep 三档输出；
- 单元测试、集成测试和真实数据验收。

默认自动组合不超过三个产品 Skill。先取得确定性事实，再由 LLM 综合表达；每轮重新检索，旧对话和用户记忆不能替代当前证据。

## 7. Knevo 对标策略

### 7.1 必须追平

- 登录或启动后直接可用；
- 持续对话；
- 搜索广度；
- 财务颗粒度；
- 清晰的长短回答；
- 任务过程可见；
- 并行取数与稳定失败恢复；
- 用户研究历史承接。

### 7.2 必须保持领先

- A 股盘面生命周期；
- 题材与个股相对强度；
- L1–L4 证据边界；
- 缺数诚实；
- 不编数值概率；
- correction/checkpoint/verdict 学习闭环；
- 研究结论可证伪；
- 证据版本和数据时点可审计。

### 7.3 当前主要差距

- W7 与海外 Web 搜索仍需长期稳定性评测；
- 财务数据需要单季、现金流、资产负债和业务分部颗粒度；
- 产品 Skill 目前主要完成 Daily Review/Daily Agent，题材、个股、消息和自选仍需正式封装；
- 跨题材长历史剧本需要扩容；
- 输出仍可能过长、偏技术，需要 quick/standard/deep；
- 数据新鲜度检查分散，尚未形成统一产品契约；
- 本地数据质量告警仍会影响真实回答。

### 7.4 暂时不追

- 大量并行 Agent 生成超长报告；
- 无限制全网搜索；
- 无溯源目标价；
- 不可审计的数值概率；
- 泛基金、保险和综合理财；
- 实时行情和自动交易。

## 8. 数据运营与证据发布

### 8.1 四条数据生产线

1. **盘面数据**：盘后同步 → 质量检查 → 新 DuckDB 快照 → 原子发布。
2. **公告新闻**：小时抓取 → 去重 → 实体识别 → 事实分类 → 事件索引。
3. **财务基线**：财报/公告触发更新，累计值、单季值和推算值分开。
4. **知识证据**：原始材料 → 候选 → 人工审核 → 已批准发布层。

Self-use 阶段可以使用全部本人有权限的私有知识资产，但 UI 仍应显示证据边界。Hosted Beta 阶段必须切换到公开发布索引，不能直接把私有知识库暴露给测试用户。

### 8.2 新鲜度契约

不得使用统一“N 天过期”。每类数据分别定义 freshness policy。

重要事实至少保存：

- `event_time`；
- `published_at`；
- `ingested_at`；
- `as_of`；
- `source_version`；
- `freshness_status: fresh | aging | stale | unknown`。

行情必须显示交易日；财报显示报告期；公告更正可以使旧结论失效；研报判断始终只作为 L1 推演；用户记忆不是市场事实。

### 8.3 证据发布状态

Hosted Beta 使用独立发布状态：

```text
candidate → reviewed → approved → published → superseded / withdrawn
```

该状态描述“能否给外部用户看”，与内容本身的 `graph_only/exposure_only/L1_L3_candidate` 和 L1–L4 证据层并行存在。

### 8.4 每日闭环

```text
盘后观察
→ 形成假设
→ 晚间补公告/新闻/卖方材料
→ 次日盘前给验证清单
→ 下一交易日盘后回检
→ correction / experience card / checkpoint verdict
```

## 9. 分阶段系统架构

### 9.1 Self-use 阶段

保留 PR #190 当前架构：

```text
React Workbench
→ FastAPI
→ Conversation/Run Supervisor
→ Product Skill / Ask / RAG / LLM
→ 本地用户态 + DuckDB + 私有知识库
```

当前阶段优先修复研究质量、数据时效、核心 Skill 和每日使用摩擦，不被外部认证与多租户基础设施阻塞。

### 9.2 Hosted Beta 阶段

本人通过 Self-use Gate 后升级为：

```text
React Workbench
→ FastAPI Web/API（认证、配额、SSE）
→ PostgreSQL（用户、对话、消息、自选、Run、配额、审计）
→ Research Worker（Skill、RAG、LLM）
→ 只读 Market Snapshot
→ Published Evidence Gateway
→ Object Storage
→ Model Gateway
```

技术取舍：

- 认证优先托管服务，不自建密码系统；
- PostgreSQL 承担用户事务，DuckDB 继续承担分析；
- Web API 不直接执行长任务；
- 大型 artifact 放对象存储；
- 首批 10–30 人不提前引入复杂分布式队列，但必须抽象 Queue 接口并持久化任务状态；
- 当前 Python、DuckDB 和长 SSE 不适合直接迁到纯 Cloudflare Workers；可用容器平台/云主机，Cloudflare 负责域名、HTTPS、WAF 和缓存。

## 10. 安全、隐私与合规边界

### 10.1 Self-use 阶段

- 继续保持本地/私有；
- BYOK 仅使用固定 Provider，不允许任意 Base URL；
- 密钥不落数据库、日志和产物；
- 输出继续阻断必涨必跌、无来源目标价和无依据概率；
- 私有知识内容不对外发布。

### 10.2 Hosted Beta 阶段

必须补齐：

- 邀请码、邮箱验证、JWT；
- 服务端可信 `user_id`；
- PostgreSQL 行级安全与跨用户越权测试；
- 会话、Run、自选、记忆、artifact 全部按用户隔离；
- Secret Manager、日志脱敏和密钥轮换；
- 用户并发与模型配额；
- Prompt 注入、SSRF、artifact 越权和私有知识泄漏测试；
- 用户可查看和删除对话、自选、记忆与上传内容；
- 默认不使用用户内容训练公共模型；
- 只展示允许公开的事实摘要、来源链接和少量合规引用；
- 正式公开或收费前进行专业法律审核。

产品允许研究解释、风险、情景与验证条件；不做代客理财、自动交易、跟单、真实仓位买卖数量建议。

## 12. 优先级

### 当前 P0：本人使用成熟

- PR #190 收口；
- 真实数据质量与新鲜度；
- 五个产品 Skill；
- 今日情报和本地自选；
- 财务与搜索关键差距；
- Knevo 对照评测；
- 10 个交易日自用验收；
- 本人明确认可。

### 内测前 P0：托管安全与隔离

- 认证与邀请码；
- PostgreSQL 用户态；
- 租户隔离；
- Research Worker 与恢复；
- 服务端密钥与配额；
- 公开证据网关；
- 安全、合规、监控和回滚。

### 留存验证后再做

- 真实持仓和组合分析；
- 基金与 ETF；
- 盘中行情；
- 团队协作；
- 收费订阅；
- 移动客户端；
- 对外 API；
- 更大规模分布式任务系统。

## 13. 明确不做

- 自动交易与跟单；
- 无溯源目标价；
- 无依据数值概率；
- 未审核知识自动发布；
- 首版覆盖所有金融品类；
- 为功能数量暴露全部内部 Skill；
- 重写 PR #190 已完成的界面；
- 在本人尚未认可核心产品时优先建设完整多租户平台。

## 14. 设计原则总结

1. 先证明产品值得每天使用，再证明外部用户能安全使用。
2. Workbench 是产品壳，五个产品 Skill 是用户能力面，内部 Skill 是实现细节。
3. 先确定性事实，后 LLM 表达；每轮重新检索。
4. 数据时点、证据状态和降级必须是一等产品对象。
5. 用户记忆承接研究，但不能覆盖新市场事实。
6. 对标 Knevo 的可用性、广度和财务颗粒度，同时保持 A 股盘面与证据纪律优势。
7. 自用成熟、Hosted Beta Readiness、Invite Beta 三个阶段分别验收，不跨 Gate 偷跑。
