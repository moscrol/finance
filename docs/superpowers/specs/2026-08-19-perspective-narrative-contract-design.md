## 0. 一句话结论

视角回答的 LLM 契约从「按九段标题顺序输出」改为「要素全覆盖 + 叙事组织」：
保留全部纪律要素（原始判断/映射/支持冲突/适用/证伪/置信度/未知项）与程序化
`answer_header`，放开段落顺序和行文方式，让正文像研究员笔记而不是填表。
compare 按**每个 KOL 各自一段**覆盖该视角要素，不是全文凑一次。

## 1. 背景与问题

### 1.1 用户反馈

2026-08-19 实测两条 run 后用户判断：「输出很生硬，不像 knevo 那样」。

- SPT 视角探针 `run_20260819_104536_844982`（8.18 盘面→次日看法）：正文为
  `【SPT视角·量能状态】…【8.18板块读法】…【次日重点观察】①②③④⑤…【证伪条件】A.B.D`
  式的分节填表。判读内容全部正确（8/8 部件可映射回 profile 字段），但读感是模板。
- 中立泳道 `run_20260819_104918_297858`（长电科技怎么看）：`条件化判断：…条件化结论：…不确定性：…失效条件：…` 同病，来源是另一条契约（见非目标）。

对照物：Knevo 蒸馏语料（q1/q15）先给判断句，判据展开服务于叙事；q15 里表格、
`条件①`、`失效场景①` 是叙事的从属，不是七要素填表。用户以「先判断、后展开」
为文风基准，不是以「禁止一切编号」为基准。

### 1.2 根因（代码证据）

1. **契约层直接规定填表**：single 契约（锚 `按以下结构输出：当前视角`）要求
   「按以下结构输出：当前视角、来源范围、KOL原始判断、当前行情映射、
   支持/冲突数据、适用条件、失效条件、置信度、未知项」——九段骨架顺序写死，
   模型忠实执行，生硬是服从而非能力问题。九段里「当前视角 / 来源范围」与
   程序化 `answer_header()` 重复，LLM 被要求再输出一遍。compare 契约
   （锚 `本轮使用多视角并列。先单列`）同构，写成「先单列、再逐一单列」。
2. **主路径治过同病，药没分给视角路径**：2026-07-01 交接记录载明
   「叙事回答编排器」解决个股深挖按模板填空——「先内部写核心矛盾句，所有
   视角必须服务核心矛盾，禁止逐项填空」；`answer_quality.py:93` 也有现成措辞
   「自然回答，不要按固定标题填空；把…融进主线」。连续研究协议
   （`episode_protocol.py`）已写「不要套固定标题、行数或段落模板」，被视角
   契约的更具体标题序压过。该成果未迁移进 perspective 契约。
3. **测试锚点分两类，只锁死第一类**：
   - **零改动**：`test_conversation_orchestrator.py` 五处
     `startswith("当前视角：…")` 锁的是 `answer_header()` 的程序化前置头
     （orchestrator 拼接，非 LLM 生成）。neutral 的
     「不得调用或模拟任何 KOL」仍在中立契约里，本单不改。
   - **本单允许改这一条**：`test_compare_context_keeps_neutral_and_kol_sections_separate`
     断言 prompt 含 `先单列“数据中立”`。compare 文案改掉「单列」后，这条必须
     改挂新稳定短语（见 §3.3.4），不是「测试零改动」。

### 1.3 不改的风险

视角功能的用户价值在「借 KOL 的眼镜读今天的盘」，文风是体验的主体。
填表式输出会让视角功能在体感上退化成结构化报表，蒸馏投入（profile 七层
schema、patch 闭环）的最后一公里被输出格式吃掉。

## 2. 目标与非目标

### 2.1 目标

- single/compare 两条视角契约的正文放开为叙事组织：第一句判断句给核心判断、
  判据展开服务主线；禁止把七要素做成独立小标题。段落内的条件编号可用。
- 纪律要素一个不丢：七要素必须全部出现在正文（顺序自由、融入行文），
  compare 按每个 KOL 段落各自覆盖，不是全文凑一次。
  三层分离（观点/事实/推理）与证据引用纪律不变。
- `answer_header()`（`当前视角：X\n来源范围：…`）保持程序化前置；LLM 不得
  再输出这两行。UI 解析与 `startswith("当前视角：")` 单测零改动。
- 可机检：要素存在性能用下方固化词表 grep 验收，评测不失去锚点。

### 2.2 非目标

- **不动中立泳道契约**（长电那条 `条件化判断/条件化结论` 标签的另一来源）——
  同病另案，本 spec 收口后再立。
- 不模仿 KOL 口癖、不改 `voice_guidance`（禁冒充本人的红线不动）。
- 不做「叙事正文 + 结构化附录折叠」的双层 UI（方案 B，本 spec 的 P2 展望）。
- 不动 BM25 召回、profile schema、patch 闭环、trace 脱敏层。
- **不动** `runtime_fallback_notice()`（仍是 `KOL原始判断：该视角未知…` 填表
  标签）。那是 LLM 未完成时的程序化兜底，不是本单叙事契约；人审不要把它
  当成契约复发。
- **不改** episode「draft 控制在 1000 汉字以内」的传输帽（锚：`draft 控制在 1000 汉字以内`）。
  P0 live 重放只跑 single；compare 不做 live 必过项（只改契约 + 单测）。

  > ⚠ **说清楚后果，别让验收时才发现**：compare 要求「中立底座段 + 每个 KOL 各一段
  > 覆盖七要素 + 综合段」，UI 允许最多 3 位 KOL，即最多 5 段。1000 汉字帽下
  > **几乎必然撞帽**。所以 P0 之后 compare 的准确状态是「契约已改、单测已过、
  > **线上仍不可用**」，不是「compare 也修好了」。放开字数需另开单。

- **P0 只修视角泳道，用户两条实测样本里的中立泳道那条（长电科技）不变。**
  技术上它属另一条契约（见上），推到 P1 合理；但用户是拿两条 run 一起说
  「输出很生硬」的——P0 交付后重跑长电仍是 `条件化判断：/条件化结论：` 填表。
  **PR 描述与验收沟通里必须写明这一点**，否则会被判成「没修好」。

## 3. 方案（P0：契约文案改写 + 验收配套）

### 3.1 顺序规则（两条「必须开头」的优先级）

`evidence_discipline` 原文保留，仍要求首选证据层缺失时「在回答开头显式声明」。
与「第一句先给核心判断」的关系钉死如下：

| 本轮证据 | 第零句 | 第一句判断句 |
|---|---|---|
| 首选层在 | （无声明句） | 本视角核心判断 |
| 首选层缺失 | `该视角首选证据（XX）本轮缺失，以下映射基于次级证据` | 本视角核心判断 |

「第一句判断句」不计声明句。声明句不是小标题，是纪律句，允许原样出现。
程序化 `answer_header` 在交付层、在 LLM 正文之前，不占第零/第一句。

### 3.1.1 single 契约新文案

```text
只允许使用下方这一位 KOL 的画像与原文召回，不得混入其他 KOL 或个人记忆。
KOL 内容属于观点层，当前检索数据属于事实层，AI 映射属于推理层，三者必须分开。
{evidence_discipline 原文不动}
写作方式：像研究员写盘后笔记那样自然行文——第一句判断句先给本视角的核心判断，
再展开判据、证据与反证。若本轮缺少该视角首选证据层，先写声明句（第零句），
再写核心判断。禁止用固定小标题逐项填空，禁止把七要素做成独立小标题；
段落内的条件编号可以使用。不要重复输出当前视角/来源范围（程序已前置）。
但以下要素必须全部出现在正文中（顺序自定，融进叙事）：
该 KOL 的原始判断（引原文）、对当前行情的映射、支持与冲突的数据（带证据引用）、
适用条件、失效或证伪条件、置信度、未知项。
观点句与事实句要可区分；原文未覆盖的问题必须写「该视角未知」，不得代替本人补写。
```

### 3.1.2 compare 契约新文案

```text
本轮使用多视角并列。先写一段数据中立的事实底座（只写本轮检索事实，不代入任何
KOL 判断），再为下方每个 KOL 各写一段自然段落；各视角不得互相污染，不得以
多数意见自动成为事实。
{evidence_discipline 原文不动}
写作方式：像研究员写对照笔记那样自然行文——每个 KOL 段落的第一句判断句先给
该视角核心判断，再展开该视角的判据与反证。若该视角缺少首选证据层，该段先写
声明句（第零句），再写核心判断。禁止用固定小标题逐项填空，禁止把七要素做成
独立小标题；段落内的条件编号可以使用。不要重复输出当前视角/来源范围（程序已前置）。
每个 KOL 段落必须各自覆盖（顺序自定，融进该段叙事）：该 KOL 的原始判断（引原文）、
对当前行情的映射、支持与冲突的数据（带证据引用）、适用条件、失效或证伪条件、
该视角的置信度、未知项。原文未覆盖的问题必须写「该视角未知」，不得代替本人补写，
也不得用其他 KOL 的判断填这个缺口。
数据中立段不含上述 KOL 要素。文末用自然段落写视角冲突与综合判断，必须标注为
AI 推理，不得写成共识事实；综合段不重复七要素清单，但要点出冲突点与综合置信。
```

要素覆盖口径：**每个 KOL 各自一段覆盖该视角的七要素**，不是把七个词在全文
各出现一次就算过。两个 KOL 就是两套要素，不是 14 个独立小标题。

### 3.2 不改的部分（明确钉住）

| 部件 | 处置 |
|---|---|
| `answer_header()` 程序化前置头 | 不动（测试与 UI 锚点） |
| `_profile_prompt` 注入块 | 不动（锚 `def _profile_prompt`；已含证据层级/推理模板。**输入可以是列表，输出才要叙事**——这是本单的分界，不要顺手把注入块也改成散文） |
| `evidence_discipline`（缺首选层大声报） | 原文嵌入新契约；与判断句的顺序见 §3.1 |
| 三层分离、citation 纪律、禁补写 | 原文保留进新契约 |
| `runtime_fallback_notice()` | 不动（见非目标） |
| episode 1000 汉字传输帽 | 不动（见非目标） |

### 3.3 验收标准

机检对象是 **LLM 正文**（`answer_header` 之后）。程序化头不含七要素词，不参与
命中；也不要把头里的「当前视角」当成模型又输出了一次结构。

#### 3.3.1 要素存在性机检（词表固化）

对单段（single=全文；compare=每个 KOL 段）以下 **8 组每组至少命中一个**。
词表故意偏松，漏检靠人审兜底；不得为了过机检把契约改回标题序。

实现时把「候选」列编成 `|` 交替正则；下表用 `/` 分隔，避免 markdown 表格吞竖线。

| 组 | 候选（任命中一个） | 备注 |
|---|---|---|
| 原始判断 | 原始判断 / 原文 / 该视角认为 / 他写过 | 「原文」过松时人审看是否真在引召回 |
| 映射 | 映射 / 对照今天 / 落到今天 / 按此看 | |
| 支持/冲突 | 支持 / 冲突 / 对得上 / 对不上 | |
| 适用 | 适用 / 成立前提 / 在什么条件下 / 前提是 | |
| 证伪 | 证伪 / 失效 | |
| 置信 | 置信 / 把握 / 信心 / 概率 | **二轮复核补**：初稿这组只有「置信」一个词，是全表最紧的一组。模型写「把握不大」「较有信心」就漏检，而漏检的下场正是实现方为了过机检把 `置信度：` 写回契约——本 spec 明令禁止的那件事。词表松一档比机检漏一次划算 |
| 未知 | 未知 / 该视角未知 | 无缺口时仍须显式收口，允许「本问未见未知项」 |
| 原文回指 | `\d{4}-\d{2}-\d{2}` **或** 本轮召回块某条 `title` 的连续 ≥4 字子串 | 日期与标题二选一；重放探针优先用召回 title |

compare 另检：全文出现 `冲突` 或 `综合`，且出现 `AI 推理` 或 `推理层`（综合段
标注为 AI 推理）。数据中立段不做七要素机检。

#### 3.3.2 文风机检（负面：禁要素小标题，不禁条件编号）

正文 **不得** 出现下列「把七要素当独立小标题」的形状（q15 的 `条件①`、
段落里的 ①②③ 不在此列）：

1. `【…】` 包裹的小标题（SPT 实测失败形）。
2. 行首（可有 markdown `#`/`##`/`**`）后紧跟要素标签再跟 `：` 或行尾，标签为：
   `KOL原始判断` / `原始判断` / `当前行情映射` / `行情映射` / `支持/冲突` /
   `适用条件` / `失效条件` / `证伪条件` / `置信度` / `未知项`。
3. 行首 `当前视角：` 或 `来源范围：`（程序已前置；再写就是双头）。

**不禁**：段落内 `条件①`、`失效场景①`、行内 ①②③、markdown 表格、
`##` 但标题不是上列要素标签（例如 `## 8.18 盘面`）。

#### 3.3.3 重放探针（P0 只跑 single）

用 `run_20260819_104536_844982` 同题（8.18 盘面→次日看法，single + sptfei）
重跑，输出满足 3.3.1+3.3.2，且判读结论与原 run 一致（量能状态机先行、
非极小量不断言新主线、证伪条件在）。compare 不做本条 live 必过。

> ⚠ **二轮复核补：这条判据会被「判读基线」污染，必须加对照跑。**
>
> 上面三个一致性检查点（量能状态机先行 / 非极小量不断言新主线 / 证伪条件在）
> 恰好等于 `intelligence/services/reading_baseline.py` 的 **SPT-A01 与 CR-03**——
> 2026-08-19 落在分支 `feat/reading-rules-baseline-batch1`（**未合 main**），
> 默认生效、注入 ask 合成与 continuous episode 两条路。
>
> - 原 run 跑在判读基线之前，那三条判读**只能**来自 SPT 画像注入；
> - 重跑若在基线之后，同样三条判读**有了第二个来源**；
> - 后果：探针会绿，但**绿的原因变了**——分不清是契约改写保住了判读，
>   还是基线在兜底。此时这条判据等于失效。
>
> **做法**：重放跑两次，只差一个 env——
>
> ```bash
> # A 组：与原 run 同条件（基线关闭），这一组才是契约改写的真实读数
> FINANCE_READING_BASELINE=0 <重放命令>
> # B 组：基线开启，反映合并后的实际生产形态
> <重放命令>
> ```
>
> **判据挂在 A 组**；B 组只做观察，用于确认两者共存不冲突。
> 若本 spec 的分支确实从最新 main 拉（§5），则该分支上没有基线代码，
> A 组等价于直接重跑——此时记录里写明「基线不在本分支」即可，不必设 env。
> **但两个改动的交互因此从未被同时验证过**：谁后合并谁做一次共存验证。

#### 3.3.4 回归

- `test_perspective_lab.py`：neutral「不得调用或模拟任何 KOL」、single
  「该视角未知」「首选证据」等保留短语的断言 **零改动**。
- **允许改这一条**：`test_compare_context_keeps_neutral_and_kol_sections_separate`
  把 `先单列“数据中立”` 改挂新文案稳定短语（建议 `数据中立的事实底座` +
  仍断言 `不得互相污染` / `视角冲突` / `AI 推理`）。

与 `knevo-distill/q15` 对照的是「先判断、后展开，表格从属叙事」，不是
「有没有编号」。用户判定「不再是填表」才算过。

### 3.4 风险与对策

| 风险 | 对策 |
|---|---|
| 模型把要素藏进长句导致机检漏检 | 七组词表宽松匹配 + 人审兜底；词表以 §3.3.1 为准，不得实现时另造 |
| 叙事化后证据引用密度下降 | 契约保留「带证据引用」；§3.3.1 含原文回指 |
| 正文仍冒出模板腔 | 负面机检禁要素小标题；若改用 `## 适用条件` 以外的变体复发，再议 P1 lint |
| 契约段变长 | 相对旧契约段会变长；相对整段 prompt（含 `_profile_prompt`）仍由画像块主导。不新增注入块。不以「±15%」做验收 |
| compare 两套要素撞 1000 字帽 | 本单不改帽、不跑 compare live；撞了另开单。**后果已在 §2.2 写明：P0 后 compare 线上仍不可用** |
| 声明句与判断句抢「开头」 | §3.1 顺序规则；声明句算第零句 |
| **人审把「判读基线」要求的编号误判成契约复发** | 合并后同一份系统提示词里会多出 `## 判读基线` 一段（7 条规则，`reading_baseline.py`）。其中 **CR-03「结论条件化并自带证伪」要求写出「当前满足几条」**，天然诱导编号输出。这**不违反** §3.3.2（段落内条件编号本就允许），人审看到编号先分清是要素小标题还是条件编号 |
| **两段注入叠加后 prompt 变长** | 初稿只算了契约段自身。合并后系统提示词还有判读基线段；两者都不占 `_profile_prompt` 的画像块主导地位，但预算评估要按叠加后算。仍不以「±15%」做验收 |

## 4. 分阶段

- **P0（本 spec）**：契约文案改写 + 验收断言/词表 + compare 那一条单测改挂。一个 PR。
- **P1（展望）**：中立泳道同病收口（另立 spec）。
- **P2（展望）**：方案 B 双层输出（叙事正文 + UI 折叠附录），等 P0 用稳后评估。
