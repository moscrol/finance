# finance-review-check：投研事实审查

只含审查方法，不携带市场事实。它在 finance-mode 之上加流程，不改其规则。目标是找错、找缺口、找过度推断，不是替用户做实盘决策。

## 使用边界

- 审查对象：金融报告、投资 memo、公司 / 行业分析、事件推演、用户贴来的投研结论、上一轮本系统的交付。
- 不审查：实盘决策本身；用户未提供原文只给标题时，不靠标题重建整条论证。
- 审查的产出必须是**可用的修订版报告**；审查反馈不能把原报告「吞掉」变成问题清单。

## 六维审查框架

- **A 数值事实**：财务指标、估值倍数、市场规模、日期、价格、概率。核心数据（摘要 / 首段 / 核心结论段引用的数值）与外围数据分级处理：核心数据偏差按本仓审查阈值分为 critical / warn，外围数据小偏差记 info。阈值在审查台账里定，不写进本文、不临场发明。
- **B 实体准确性**：公司短名 / 全称 / 代码 / 易混淆实体（同名不同公司、同一集团不同上市主体）。消歧错误或代码错误 → critical；短名未澄清 → warn。用实体解析工具消歧。
- **C 来源可追溯**：带「据研报 / 据公告 / 预计 / 分析师认为」的强论断是否标出处。不可追溯的强论断 → critical；出处模糊 → warn。
- **D 逻辑自洽**：证据到结论的链是否成立，有无推理跳跃、前后矛盾。区别于 C：C 看外部证据对不对得上，D 看内部逻辑链。
- **E 时效性**：数据是否过期、政策 / 财报是否已有新版本、日期与截至日标注是否齐全、有没有用后来才知道的信息解释当时。
- **F 完整性**：按报告类型的骨架核对「必有段」是否齐全（对照对应专项的输出骨架：复盘、个股、行业、事件各自的骨架）。

## 流程（逐步推进，不要跳步）

1. **解析输入**：拿到待审文本，判主题（个股 / 行业 / 事件 / 观点）与报告类型，找到对应专项的骨架作为 F 维的尺子。
2. **预扫**：六维快扫候选问题点——引用、数字、实体、日期、强论断。短文本且零候选 → 直接 PASS，不为了审查而审查。
3. **真值检索**（并行发射）：数值用结构化数据与已披露财务；实体用实体解析与图谱；来源 / 历史用个人记忆与证据索引；公告与新闻先用公告查询与新闻检索；不足时再用网页检索与取页补全。记忆与数据源冲突时，数字以数据源为准。
4. **Issue 归集**：按维度 + 严重度排序；每条带原文引用、位置、来源链、修正建议。
5. **修订**：PASS → 不改；WARN → 改所有 warn 级；FAIL → 改 warn + critical 后重验。**只改有明确修正文本的事实性 / 标注性错误，不改报告结构、立场和核心结论**；核不动的保留争议与缺口，不伪造修订值。
6. **输出**：修订版报告为主体 + 折叠审查详情。

## 输出格式

```text
## Review Verdict: <PASS | WARN | FAIL>
**摘要**: <一到两句整体质量>  **修订**: <已修订 N 处 | 无需修订>

---
<修订版报告全文（PASS 时原样输出）>
---
<details><summary>📋 审查详情与修订记录</summary>
按 A / B / C / D / E / F 分组列 issue：原文 / 位置 / 来源 / 偏差 / ✏️ 已修订为；空维度省略。
末尾给修订记录表。
</details>
```

要点：报告在前、审查在后；PASS 时极简（verdict 一行 + 原报告）；每条已修订的 issue 标 ✏️；前端不支持折叠时退化为分隔线后的附录。

## 来源标注与红线

- 修订依据标真值来源；审查结尾说明哪些 issue 与数据源对齐、哪些只是内部逻辑问题。记忆证据区分用户记忆与共享来源。
- 来源自述不等于独立核验；多家转载不构成交叉验证。
- 核心事实尚未核实或错误未解决时，不宣称审查通过。
- **FAIL 阻塞写回**：verdict 为 FAIL 时不得提示把结论写入记忆或画像；PASS / WARN 时可提示用户确认后写回。
- 用户要求修订报告时交付修订正文并附修改记录，保留未解决问题；不以问题清单代替交付，也不静默改变原作者立场。

## 交付前自检

1. 每条 issue 都有原文位置和来源链吗？
2. 修订只动了事实与标注，没动结构、立场、核心结论吗？
3. verdict 与最高严重度一致吗（有 critical 未解决就不能是 PASS）？
4. 修订版报告是完整正文，不是摘要或清单吗？
5. 审查结尾说清了哪些核了、哪些核不动了吗？

## 输出契约与交付后

交付必须以完整修订版报告为主体，不能只发问题清单或 verdict。交付后（用户触发，不主动执行）：非 FAIL 时可提示用户确认后把修订结论写回记忆；FAIL 时阻塞写回。

## 追问建议

结尾给不超过四条、用户口吻、每条不超过二十字的追问：纵深（从未解决的 issue 生成，必选）、横向、操作或替代路径、验证。
